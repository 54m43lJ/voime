WINDOWS — Voime 平台适配评估

README USER CORE PROVIDER BUILD

评估基线：dev/fcitx@07d9cfa · 2026-10-30。 本文是对当前设计的静态审查与可行性判断，不是 Windows 实测报告；所有 Windows API 行为仍需用最小原型验证。

1. 结论

↑

1.1 一句话结论

不能直接套入 Windows。当前设计的“识别引擎 + 守护进程”与“输入前端”确实已经分层，但只把 Fcitx 前端隔离了出去，没有把桌面输入集成抽象成可替换的平台接口。Windows 上需要新建输入前端；识别、VAD、CTC、标点、会话状态与 IPC 协议可以大量复用。

“语音 → 文字 → 输入”的闭环可行，但要分两种产品形态：后台听写工具（全局热键 + 文本注入）可以较快闭环，覆盖多数普通桌面应用；真正的 Windows 输入法（TSF 文本服务）也能闭环，但需要重写为进程内 COM 组件；若按 keyboard TIP 注册，还会改变“后台 addon、不注册输入法”的使用方式，speech TIP 是否能并行则需验证。

1.2 结论表

问题结论依据
能否把现有代码直接编译到 Windows？ 不能。 voimed / voime 直接使用 std::os::unix::net::UnixStream、UnixListener 与 Unix 权限位；fcitx-addon 是 Fcitx5 C++ 插件，CMake 依赖 Fcitx5Core。
识别引擎是否能复用？ 可以，复用度高。 voime-core 的音频、重采样、VAD、CTC、标点、分段器与 pipeline 不依赖 Fcitx；cpal、ONNX Runtime、kaldi-native-fbank、rubato 都有 Windows 路径。
IPC 协议是否能复用？ 可以，但传输层要换。 消息是换行分隔的 JSON，与平台无关；Unix socket 必须替换为 Windows 命名管道或其他本机传输。
能否闭环“语音 → 文字 → 输入”？ 可以，但有覆盖边界。 全局热键 + SendInput 能覆盖大量 Win32 / Chromium / Electron / Office 类应用；提权窗口、游戏、部分终端与 UWP 需要单独验证。TSF 可以获得更可靠的提交与目标上下文，但激活方式不同。
当前设计算不算“足够解耦”？ 引擎层够，平台输入层不够。 进程边界、协议、模式/分段状态机是好的；但传输、角色命名、单前端假设、预览表面、音频生命周期、安装与自启动仍与 Linux/Fcitx 绑定。
建议先做哪条路？ 先做 MVP，再决定是否做 TSF。 先用后台听写验证“目标绑定 + 提交可靠性 + 用户接受度”，成本低；如果产品要求系统级输入法体验，再做 TSF 第二阶段。

1.3 三个判断

  • 可复用：音频采集后的整条识别链路、会话状态机、Partial / Final / State 消息语义、TUI 的大部分终端逻辑。
  • 必须重写：Fcitx addon、热键/焦点/目标绑定、临时窗口、文本提交、配置与安装/自启动。不能把 fcitx-addon 逐行翻译成 Windows；它只能作为行为规格。
  • 最大风险：SendInput 在真实应用中的覆盖率与焦点竞态；TSF 键盘 TIP 的“必须被选为当前输入法”、speech TIP 是否能并行的未知性，以及多进程客户端模型；还有 Windows 麦克风隐私、蓝牙耳机与提权窗口带来的边界。

2.2 判定标准

标准要回答的问题

2.3 先区分两种“输入法”

“输入法”在 Windows 上通常指可被系统选中的 IME（Text Services Framework 文本服务）；而“语音听写工具”是后台程序，用全局热键把识别文本注入当前焦点。两者都能把文字送进应用，但系统身份、目标模型、提交可靠性和使用方式不同。

形态系统身份用户操作本项目对应
后台听写工具 普通桌面进程 + 全局热键 在任意应用按热键说话，文字注入当前焦点 方案 A；最接近现有“后台 addon”的 UX
Windows 输入法（IME） TSF 文本服务（进程内 COM DLL） 用户把 Voime 选为当前输入法后说话；或通过输入法切换进入 方案 B；系统集成更完整；按 keyboard TIP 时不再是“后台旁路”
  • 现有 README 的非目标明确写了“不支持 Linux + Fcitx5 之外的平台形态”。本文评估的是：若要改变这个非目标，现有设计离 Windows 有多远。
  • “闭环”不要求必须有临时文本窗口；预览是体验项，最终提交才是闭环的必要条件。

3.3 解耦得好的地方

  • 进程边界清楚：Fcitx 进程只负责键盘、焦点、临时窗口与提交；voimed 拥有音频、模型、pipeline 与会话历史；TUI 只是客户端。这个划分本身可以直接延续到 Windows。
  • 核心不依赖输入法框架：voime-core 没有 Fcitx 类型；音频、VAD、CTC、标点、分段器都能独立测试。
  • 目标策略留在前端：daemon 只分配 segment_id 并广播 SegmentStarted / Partial / Final；目标绑定、失焦判断、提交由前端完成。Windows 前端可以按自己的目标模型实现，这是最重要的可替换点。
  • 模式与热键由前端拥有：Mode / Hotkey 从 addon 配置通过 Hello / Configure 同步给 daemon，daemon 不解析命令行模式。Windows 前端可以继续拥有这两个配置。
  • 临时结果与最终结果分离：Partial 可丢、Final 不丢的背压策略与平台无关；Windows 浮层/TSF UI 只需要消费同一条消息。
  • 无异步运行时：线程 + crossbeam 的模型容易换成命名管道读写线程，不需要引入 tokio。
  • 模型包路径相对化：manifest.json 使用相对路径，resolve_inside 还拒绝绝对路径与 ..；Windows 上只需要换默认目录。

3.4 仍然绑死的地方

泄漏点现状Windows 影响建议处理
本机传输 voimed 用 UnixListener / PermissionsExt；voime 用 UnixStream；fcitx-addon 直接使用 AF_UNIX / sockaddr_un。 Rust 侧无法编译；Windows 需要命名管道或 uds_windows 包装的 AF_UNIX。 在 voime-ipc 增加 Endpoint 与传输实现；Unix socket / Windows named pipe 双后端。
角色命名 Role::Fcitx、FcitxConfig、AddonState、Snapshot.addon、错误语义 FcitxUnavailable / AddonNotLoaded。 Windows 前端可以硬套这些名字，但日志、TUI 文案和协议语义都可疑；后续多前端会更乱。 泛化为 Frontend / FrontendConfig / FrontendState；保留旧值作为兼容别名并升级协议版本。
单前端假设 IpcServer::set_role 只允许一个 Role::Fcitx；daemon 的 addon 状态是单值。 方案 A 够用；方案 B 的 TSF DLL 会加载到多个应用进程，需要多个客户端或一个代理层。 MVP 保持单前端；TSF 阶段增加 Role::TextService 与目标认领/路由。
目标模型 InputContext 弱引用 + hasFocus()；提交直接调用 commitString。 Windows 只能用 HWND/UIA 或 TSF context 重建；没有“输入框对象”可直接复用。 把目标抽象为前端私有类型；协议不携带目标对象，只携带 segment_id 与事件。
预览表面 Fcitx InputPanel 的 preedit。 Windows 需要自绘浮层（WS_EX_NOACTIVATE / 置顶 / DPI）或 TSF 组合/候选 UI。 保持 Partial 协议；在 Windows 前端实现独立的 preview 模块。
音频生命周期 daemon 启动即打开麦克风流并保持播放；没有按段开关。 Windows 会常亮麦克风指示；蓝牙耳机会被拉入 HFP；隐私设置拒绝时 daemon 直接启动失败。 增加按需开流/关流或至少可配置；启动失败时给出 Windows 隐私诊断。
采样格式 audio/capture.rs 只匹配 I16 / U16 / F32；其它格式返回 UnsupportedSampleFormat。 WASAPI 设备可能报告 I32 / U32；会直接不可用。 补充 I32 / U32（以及必要时 I8/U8）转换；或统一用 cpal 的样本转换。
设备选择 按设备名精确匹配；默认设备由 cpal 决定。 Windows 设备友好名可能重复、随语言变化；默认设备与“通信设备”可能不同。 支持 endpoint ID / 索引；明确默认设备角色；doctor 显示实际设备。
配置与路径 XDG_DATA_HOME / XDG_RUNTIME_DIR / HOME；Config 里直接放 socket: PathBuf。 Windows 没有这些变量；命名管道不是文件路径。 平台目录模块（LOCALAPPDATA / APPDATA）；把 endpoint 移出 voime-core::Config。
诊断 voime doctor 读 /proc、/usr、XDG 配置，检查 Fcitx 进程与 addon。 Windows 上全部失效。 写 Windows doctor：麦克风隐私、设备、命名管道、前端进程、模型、TSF 注册（若做 B）。
安装/自启动 systemd user unit、bash 安装脚本、fcitx5 -r。 不应把 daemon 装成 Session 0 服务：它无法可靠访问交互用户会话的麦克风，也破坏隐私边界；需要登录启动项/托盘。 每用户安装器 + 登录启动；前端负责拉起 daemon；不要用 Windows 服务采集音频。
热键语义 Fcitx key 语法，默认 Super+F2；由 Fcitx 只在有文本焦点时消费。 Win+F2 可能被系统保留；全局热键会吞掉整个系统范围的组合键；PTT 需要 key-up。 换默认组合（如 Ctrl+Alt+Space）；自己实现热键解析；PTT 用低级钩子或轮询 GetAsyncKeyState。
编码 UTF-8 字符串，commitString 直接接收。 SendInput 与 TSF 都使用 UTF-16；emoji 需要代理对。 前端统一做 UTF-8 → UTF-16 转换；按 UTF-16 单元拆分注入。
错误语义 NoInputContext、CommitTargetLost、FcitxUnavailable、AddonAbiMismatch 等。 部分错误在 Windows 没有对应物；用户文案不应出现 Fcitx。 拆成通用 FrontendUnavailable / TargetLost / CommitFailed，平台细节放日志。

判定项结果说明

前端可替换性部分协议语义支持替换，但传输、角色、单前端假设与目标抽象没有完成。

4. Windows 输入路径

↑

4.1 方案 A：后台听写工具（全局热键 + 文本注入）

  • 前端是普通桌面进程，不需要注册为 Windows 输入法；daemon 继续拥有音频与模型。
  • 提交不是 Fcitx commitString，而是向当前焦点窗口注入 UTF-16 文本。

流程

用户按下热键
└── Windows 前端
    ├── 记录前台窗口 + 焦点元素
    ├── 发送 Start / Stop 到 voimed
    └── voimed
        ├── 采集 → VAD → CTC → 标点
        ├── 广播 Partial（前端浮层显示）
        └── 广播 Final
            └── Windows 前端
                ├── 清除浮层
                ├── 校验前台窗口 / 焦点元素仍是目标
                └── SendInput(KEYEVENTF_UNICODE, UTF-16)

实现要点

能力Windows 实现复用现有代码
热键RegisterHotKey 适合 Toggle；PTT 需要 WH_KEYBOARD_LL 获取 key-up，或定时轮询 GetAsyncKeyState。语义复用：Hold / Toggle / Continuous；实现重写。
目标绑定GetForegroundWindow + GetGUIThreadInfo 取焦点 HWND；再用 UI Automation GetFocusedElement 取控件与 RuntimeId。绑定/失焦策略可参考 addon，但不能复用代码。
音频cpal 的 WASAPI 后端；需处理 I32/U32、默认设备与隐私设置。采集之后的 pipeline 直接复用。
临时窗口无激活、置顶、点击穿透的分层窗口（WS_EX_NOACTIVATE / WS_EX_TOOLWINDOW / WS_EX_TRANSPARENT）；按 DPI 与多显示器定位。只复用 Partial 消息与显示策略，UI 重写。
提交SendInput + KEYEVENTF_UNICODE；长文本分批；提交前检查目标。Final 文本与 segment_id 复用。
失败处理daemon 不可用、无麦克风、目标失焦、注入失败都回到“不误提交”策略，最终文本保留在 daemon 历史/TUI。错误策略与状态机复用。

边界与限制

场景结果说明
普通 Win32 / WinForms / WPF通常可用焦点 HWND 明确，SendInput 一般能到达编辑控件。
Chromium / Electron / Office通常可用，需实测焦点元素常是子控件或 contenteditable；UIA 能帮助绑定，但仍可能有焦点竞态。
Windows Terminal / 控制台需实测终端可能使用不同的输入路径；部分 TUI 程序会拦截合成输入。
UWP / 商店应用需实测沙箱与焦点模型不同；不能用“普通 Win32”假设。
提权窗口（管理员控制台、任务管理器）通常不可用UIPI 会阻止普通完整性进程向高完整性窗口注入；除非前端也提权。
游戏 / Raw Input / 反作弊通常不可用合成输入可能被忽略或拦截；这不是本项目应承诺的场景。
密码框可能注入SendInput 不知道输入框语义；只能做 best-effort 的 UIA 检测。
同一窗口内切换输入框可能误提交前台 HWND 不变但焦点元素变化；需要 UIA RuntimeId 或 caret 校验。
锁屏 / UAC 安全桌面不可用与现有 Linux 非目标一致，不承诺。
  • 方案 A 的“输入法”身份不完整：没有 composition、没有系统输入法列表、没有候选/语言栏集成；它更像“语音听写工具”。
  • 如果产品接受“在支持的桌面应用里按热键说话即可上屏”，方案 A 可以闭环；如果要求“像微软拼音一样被系统选中、在所有应用中可靠工作”，方案 A 不够。

4.2 方案 B：TSF 文本服务（真正的 Windows 输入法）

  • TSF DLL 加载到每个使用 TSF 的目标应用进程内；它不应自己持有 740 MiB 模型，仍然通过命名管道与 daemon 通信。
  • 提交发生在应用进程内，使用该应用的 ITfContext，比跨进程注入更接近系统输入法。

TSF 侧需要实现的接口

接口 / 机制作用
ITfTextInputProcessor / ITfTextInputProcessorEx文本服务生命周期：激活、停用；取得 ITfThreadMgr。
ITfThreadMgrEventSink跟踪焦点上下文、文档变化；决定当前目标 ITfContext。
ITfKeyEventSink在 Voime 是当前输入法时接收按键；处理热键并放行普通按键。
ITfContext::RequestEditSession / ITfEditSession在目标上下文里执行读写编辑；提交文本必须走 edit session。
ITfRange::SetText / Collapse把最终文本写入选区或组合范围。
ITfContextComposition / ITfComposition可选的组合/preedit；与现有“只用输入面板、不用客户端 preedit”的设计冲突。
ITfUIElementSink / candidate UI可选的候选/预览窗口；实现成本高，也可以先用独立浮层。
ITfInputProcessorProfileMgr注册/激活语言 profile；决定 Voime 何时成为当前输入法。
COM 注册 + InprocServer32CLSID、线程模型、DLL 路径；通常需要管理员权限，且要同时提供 x86 / x64 DLL。

两种 TSF 注册方式

注册类别激活方式与键盘输入法的关系需要验证
keyboard TIP（GUID_TFCAT_TIP_KEYBOARD） 语言栏 / Win+Space 选中，成为当前键盘输入法 互斥；Voime 激活时，微软拼音等键盘输入法不处于活动状态 提交、焦点、按键、切换体验；普通按键是否全部放行
speech TIP（GUID_TFCAT_TIP_SPEECH） 作为语音文本服务注册；能否与 keyboard TIP 同时激活没有稳定的公开保证 可能并行，但不能按“已成立的后台旁路”设计 能否同时激活、是否收到焦点上下文、是否收到热键、应用覆盖
  • Windows 自带的语音输入/听写可能使用了与 keyboard TIP 不同的路径；这不是可直接复制的实现证据，必须用 TSF 原型验证。
  • 如果 speech TIP 能稳定并行，它会是比 keyboard TIP 更接近现有后台 UX 的方案；如果不行，就必须接受输入法切换。

TSF 方案的关键约束

约束影响
键盘 TIP 必须成为当前输入法；speech TIP 的并行能力未验证 若注册为 keyboard TIP，用户需要把 Voime 选为输入法（语言栏 / Win+Space），或者由前端用系统快捷键切换；这会与微软拼音、搜狗等键盘输入法互斥。若注册为 speech TIP，是否能与另一个键盘输入法同时激活、是否仍能稳定收到焦点上下文与按键，需要原型验证，不能直接当作后台旁路。
TSF DLL 是进程内组件，按应用位数加载 需要 x86 与 x64 两份 DLL；安装/注册比普通桌面程序重；每个应用进程都会加载。
多客户端 一个 TSF DLL 实例只对应一个应用进程；daemon 现在只允许一个 Role::Fcitx 客户端。需要多客户端角色或代理/路由层。
提交语义 ITfRange::SetText 仍然可能失败（只读、选区变化、上下文销毁）；必须处理 edit session 失败，不能假设一定成功。
预览语义 用 composition 会让应用渲染 preedit，违背当前“不用客户端 preedit”的约定；用候选/UIElement 实现复杂；用独立浮层则又回到方案 A 的自绘窗口。
更新 DLL 被大量应用加载；升级时替换文件可能失败，运行中的应用继续用旧版本。需要版本化 DLL、注册切换和“重启应用/注销”策略。
覆盖范围 仍不覆盖不使用 TSF 的应用（部分游戏、部分终端/遗留程序）和锁屏/安全桌面。

TSF 方案的价值

  • 目标上下文、焦点、选区由系统框架提供，不需要靠前台窗口猜测；目标丢失更容易判断。
  • 提交在应用进程内完成，不依赖 SendInput 的全局注入；对提权应用、UWP、Office/Chromium 等通常更可靠（前提是 DLL 被加载）。
  • 可以做真正的 composition / 候选 UI / 语言栏集成，系统身份是“输入法”。
  • TSF 不是“把 Fcitx addon 换成 Windows API”那么简单：它是另一套生命周期、激活模型与进程模型。
  • 不要设计“按热键临时把前台线程切到 Voime、提交后切回”：TSF profile 激活是线程级的，跨进程切换没有稳定的公共 API；模拟 Win+Space 容易破坏用户当前输入状态。
  • 如果产品不能接受“用户需要切换到 Voime 输入法”这一 UX，那么 TSF 可能不是正确答案，方案 A 反而更贴近现有体验。

4.3 方案 C：混合与回退

手段适用问题
UI Automation ValuePattern.SetValue 标准 Edit 控件、部分 UWP 控件 绕过键盘/输入法语义；不触发所有变更事件；对 contenteditable / 自定义控件无效。
剪贴板 + Ctrl+V SendInput 失败的普通应用 污染用户剪贴板与剪贴板历史；需要恢复；提权窗口仍可能失败；不适合密码/敏感内容。
EM_REPLACESEL / 控件消息 标准 Win32 Edit / RichEdit 只覆盖特定控件；跨进程消息与 UIPI 限制；维护成本高。
TSF 组合 + 自定义候选窗口 真正的输入法体验 实现量大；与现有“不用客户端 preedit”的约定冲突。
  • 方案 C 应作为方案 A 的兜底，不应作为主路径；剪贴板回退必须默认关闭或明确提示。
  • 不建议用 loopback TCP 作为默认 IPC：会触发防火墙提示、端口冲突，且本机任意进程可连接；命名管道更容易做用户级 ACL。

5. 闭环判定

↑

5.1 闭环定义

本文把“闭环”定义为：用户触发后，系统自动完成采音、VAD 分段、识别、标点，并把最终文本提交到同一目标输入位置；失败时可见、可恢复，不需要用户手工复制粘贴；运行期不联网。

5.3 方案 A 的闭环结论

结论内容
能闭环的场景普通 Win32 / WinForms / WPF、Chromium/Electron、Office 类应用、部分终端；目标窗口在录音期间保持前台与焦点；用户接受“语音听写”而非“系统输入法”。
需要降级的场景提权窗口（不注入了，只保留历史）、游戏/Raw Input、部分 UWP/终端、同一窗口内焦点切换；提交失败时提示用户手动从 TUI/历史复制。
不能承诺的场景锁屏、UAC 安全桌面、所有应用 100% 覆盖、密码框安全、长文本零延迟。
总体判断可以形成产品级闭环，但应明确“支持的桌面应用集合”，不要宣称“Windows 通用输入法”。

5.4 方案 B 的闭环结论

结论内容
能闭环的场景TSF 应用；Voime 是当前输入法；目标上下文明确；提交走编辑会话；可做 composition / 候选/预览。
仍然不覆盖非 TSF 应用、部分游戏/终端、锁屏/安全桌面；输入法切换期间的空窗。
主要代价用户必须切换到 Voime 输入法；32/64 位 DLL、COM 注册、多客户端、升级与应用重启；工程量显著大于 A。
总体判断技术上更“像输入法”，但与现有“后台 addon、不注册输入法、普通输入法照常”的产品约定冲突；需要产品层面先接受新的交互模型。

6. 需要改造的边界

↑

6.1 P0：做 Windows MVP 之前必须完成

#改动落点验收
1 传输抽象：把 Unix socket 从 daemon/client 中抽出，定义 Endpoint 与读写接口；Windows 后端用命名管道。 voime-ipc 新增 transport 模块；voimed::ipc_server、voime::client 改为泛型/枚举端点。 Linux 行为不变；Windows 上 daemon 与客户端可握手、收发 JSON lines；命名管道只允许当前用户。
2 协议去 Fcitx 化：Role::Fcitx → Frontend，FcitxConfig → FrontendConfig，AddonState → FrontendState；旧值保留兼容别名。 voime-ipc、voimed、voime、TUI 文案、协议版本。 旧 addon 仍能连接（兼容期）；新前端使用新角色；日志/快照不再出现 Fcitx 专用词。
3 平台目录与配置：模型、日志、配置、端点按平台解析；socket: PathBuf 从 voime-core::Config 移出。 voime-core::config、voimed、voime、doctor。 Windows 默认 %LOCALAPPDATA%\voime\...；Linux 默认路径不变；CLI 支持 --endpoint。
4 音频适配：补 I32/U32；设备按 endpoint ID/索引选择；评估按段开流与常开流的取舍；隐私拒绝给出明确错误。 voime-core::audio::capture、config、voimed 启动流程、doctor。 Windows 上内置麦克风、USB、蓝牙至少各一台可用；设备切换/拔出有可读错误。
5 构建与 CI：用 cfg 隔离 Unix 专属代码；Windows 构建产出 voimed.exe、voime.exe 与 onnxruntime.dll；模型安装脚本支持 Windows。 Cargo.toml、tests/、scripts/、tools/install_models.py、CI。 cargo test 在 Windows 通过；Linux 行为不变；模型校验通过。
6 Windows 前端 MVP：托盘/后台进程、热键、目标绑定、浮层、SendInput、失焦取消、daemon 重连。 新 crate（例如 crates/voime-windows/）或独立 windows-frontend/；使用 windows crate。 在验收应用集合中完成“按热键说话 → 浮层 → 最终文本上屏”；目标失焦不误提交。
7 生命周期与安装：每用户安装、登录启动、单实例、日志、卸载；不要使用 Session 0 的 Windows 服务采集音频。 安装器、启动项、voimed 启动方式、托盘菜单。 重启登录后自动可用；daemon 崩溃可由前端拉起；卸载干净。
8 安全基线：命名管道 DACL（当前用户）、拒绝远程客户端、键盘钩子只处理配置热键且不记录、提交前目标校验、二进制签名。 传输层、Windows 前端、安装器。 同机其他用户不能连接；无按键/音频/文本落盘；安全软件不误报（需签名与说明）。

6.2 P1：决定做 TSF 后必须完成

#改动落点验收
1 多客户端协议：新增 Role::TextService（或等价代理模型）；允许多个 TSF DLL 连接，daemon 按 segment_id / 目标认领路由 Partial / Final。 voime-ipc、voimed::ipc_server、daemon。 两个以上 TSF 应用同时打开时，只有目标上下文提交；无重复提交。
2 TSF DLL（x86 + x64）：ITfTextInputProcessor、ITfThreadMgrEventSink、ITfKeyEventSink、edit session、ITfRange::SetText。 新 tsf/ C++ 工程；COM/CLSID 注册；DLL 签名。 在 Notepad、Word、Chrome、VS Code、Windows Terminal 中完成提交与焦点丢失处理。
3 激活模型：决定 Voime 是 keyboard TIP（用户主动切换）还是 speech TIP（先验证并行能力）；不要假设可以无感旁路。 TSF profile 注册、托盘/语言栏、用户文档。 用户能清楚地知道何时 Voime 在接收按键；不会误吞普通输入。
4 预览：选择 composition、candidate UI 或独立浮层；明确是否接受客户端 preedit。 TSF DLL / 前端浮层。 Partial 显示与 Final 清理符合现有 Toggle/PTT 语义。
5 安装/升级：TSF 注册需要管理员；32/64 位 DLL；版本化；运行中应用加载旧 DLL 的处理。 安装器、注册脚本、升级流程。 升级后可回退；旧 DLL 不阻塞新 daemon；用户知道需要重启哪些应用。

6.3 P2：可选增强

  • UIA ValuePattern / 剪贴板回退，仅对白名单应用启用。
  • 按光标位置显示浮层（UIA TextPattern / GetGUIThreadInfo 的 caret 矩形）；多显示器与 DPI 适配。
  • Windows 10/11 不同版本的兼容性；ARM64 评估。
  • 无网络遥测之外的本地诊断包（默认关闭，不包含音频/文本）。

6.4 推荐实施顺序

1. 传输 + 配置 + 音频 + CI
   └── 让 voimed / voime 在 Windows 上编译、启动、连接、采集

2. Windows 前端 MVP
   ├── 托盘 + 热键 + Start/Stop/Toggle
   ├── 目标绑定（前台窗口 + UIA）
   ├── 浮层（Partial）
   └── SendInput（Final）

3. 真实应用验收
   └── 通过 → 作为“语音听写工具”发布
       不通过 → 缩小支持范围，或进入 TSF 评估

4. TSF 原型（仅当产品要求系统级输入法）
   ├── Notepad 单应用提交
   ├── 多应用 + 多客户端
   ├── 32/64 位 DLL / 注册 / 升级
   └── 通过 → 产品化；不通过 → 保持 MVP

6.5 不建议的做法

  • 不要逐行移植 fcitx-addon。它的价值是行为规格（热键、目标、预览、提交顺序），不是可移植代码。
  • 不要用 Windows 服务承载音频。Session 0 无法可靠访问交互用户会话的麦克风；用登录启动的每用户进程。
  • 不要把 loopback TCP 作为默认 IPC。防火墙提示、端口冲突、任意本机进程可连接；命名管道更合适。
  • 不要假设 SendInput 到处可用。先把支持矩阵写清楚，再决定是否投入 TSF。
  • 不要在 TSF 中假设“后台旁路”。按 keyboard TIP 注册时，TSF 文本服务必须是当前输入法；speech TIP 能否并行仍需验证，不能先按旁路设计。

目标/提交 录音期间切换窗口；同窗口切换输入框；最小化/关闭目标；只读控件；密码框；长文本；emoji/中英混排；剪贴板回退（若启用）。
故障 daemon 未启动/崩溃/重启；模型缺失/损坏；管道断开；前端崩溃；磁盘满；麦克风被占用。
安全/隐私 其他用户连接管道；远程客户端；网络抓包确认无出站；检查临时目录/日志/崩溃转储；键盘钩子不记录非热键。
性能 PTT 按下到开始录音延迟；Final 到上屏延迟；10/20/30 s 语音 RTF；内存占用；首次模型校验时间；长时间连续模式稳定性。

7.4 仍需实测的未知项

  • SendInput 在 Chromium、Electron、UWP、Windows Terminal、Office 中的真实成功率与延迟。
  • 中文输入法开启时 Unicode 注入是否被拦截；是否需要在注入前切换输入法状态。
  • 提权窗口、RDP、多会话下的行为；是否需要可选的提权前端。
  • TSF 在目标应用中的激活、焦点、composition、只读/密码输入域的实际表现。
  • 蓝牙耳机按段开流与常开流的音质/延迟权衡。
  • Windows Defender / SmartScreen 对键盘钩子与注入行为的拦截策略。
  • 模型在 Windows 上的 RTF 与内存占用是否与 Linux 验收值一致。

8. 建议

↑

如果产品目标是…建议路径原因
“在 Windows 上按热键说话，文字进入当前应用” 方案 A；先做 P0，再做 MVP。 最接近现有后台 addon；复用识别链路；工程量可控；可先验证真实应用覆盖率。
“像系统输入法一样，被选中后在所有应用可靠工作” 方案 B；先做 TSF 单应用 spike，再决定是否产品化。 只有 TSF 能提供系统输入法身份与 context 级提交；但 keyboard TIP 的激活方式、speech TIP 的并行能力、32/64 位 DLL、多客户端与升级成本都需先验证。
“先不确定，想看 Windows 是否值得投入” 先完成 P0 + MVP 的目标/提交验证；用数据决定是否进入 TSF。 TSF 的最大风险不是识别，而是输入法激活与覆盖；MVP 能以较低成本暴露这些问题。

工程建议：把“平台输入集成”正式抽象成一层，而不是在 daemon 里加 #[cfg(windows)] 分支。当前最值得做的重构是传输抽象与角色/协议去 Fcitx 化；这两项完成后，Windows 前端、TUI、未来 TSF 都能复用同一套会话协议。

产品建议：在文档和 UI 中明确区分“语音听写工具”和“Windows 输入法”。如果选择方案 A，不要宣称“通用输入法”；如果选择方案 B，要提前接受“用户需要切换到 Voime 输入法”的交互变化。
