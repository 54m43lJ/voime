1. WHAT & WHY

↑

1.1 IDEAL：要解决的问题

Qwen GPU worker 是独立进程，由 daemon 启动、握手、发送完整语音段、读取最终文本、处理错误并关闭。 如果 daemon 与 worker 各自定义 framing、JSON 字段、错误码与关闭顺序，协议就会随实现漂移。 voime-gpu-common 把 daemon 与 worker 之间的 frame 协议——帧格式、请求 / 响应、错误码与协议生命周期辅助——收敛为一个 不依赖推理 runtime 的库；模型加载与推理仍留在 worker。

1.2 GOAL：什么算成功

  • GPU worker 与 daemon 使用同一套帧布局：长度前缀 + UTF-8 JSON header + 长度前缀 + f32le PCM。
  • 请求与响应类型只在本 crate 定义；worker 与 daemon 不复制消息结构。
  • 握手、加载、单段识别、取消与关闭的消息顺序明确，daemon 用同一段代码服务 GPU 后端。
  • 错误码稳定且可执行：daemon 不解析错误文案，就能决定标记后端不可用、回退 CPU 或重启 worker。
  • 识别文本只出现在 Result.text 中；日志只记录长度、耗时、错误码与后端名称，加载失败可附加模型路径与 SHA 前缀。
  • worker 协议与前端 IPC 相互独立；本协议的变化不提升 voime-ipc 的协议版本。

1.3 非目标

  • 不加载模型、不解析模型 manifest、不校验权重 SHA；这些属于 worker。
  • 不含推理 runtime，不链接 ORT / llama.cpp / GGML；本 crate 只依赖 serde、serde_json 与 anyhow。
  • 不做 VAD、Preview、Partial、分段或流式识别；GPU worker 只接收完整语音段。
  • 不做前端 IPC、热键、目标绑定、临时窗口或文本提交；前端消息归 voime-ipc USER。
  • 不负责 spawn、杀进程、重启退避与显存回收；这些属于 voimed 的 worker 生命周期。
  • 不采集音频、不转换采样率；输入必须是 16 kHz 单声道 f32 PCM。
  • 不做标点、大小写或文本后处理；worker 返回的文本已经是最终文本。
  • 不记录识别文本、不写音频或历史到磁盘。
  • 产品级术语见 根 USER §1；帧格式与错误码见 USER。
  • 本 crate 没有直接外部 provider，因此没有 PROVIDER 文档；依赖库见 CORE §3。

2. 用户交互

↑

本库没有终端用户入口。它的“用户”是 daemon 与 GPU worker；终端用户只通过 daemon 观察 GPU Final 成功或回退 CPU 的结果，不直接接触本协议。

调用方交互契约
voimed 按 final.backend 启动 worker，完成 Hello / Ready 握手；发送 Transcribe 与 PCM；等待 Result / Error；必要时 Cancel；退出时发送 Shutdown 并等待 Bye。 USER §4 · voimed USER §4.4
voime-gpu-qwen3 读取 Hello / Transcribe / Cancel / Shutdown；加载自己的 runtime 与模型；写 Ready / Result / Error / Bye。模型目录、runtime 与输出清洗由本 worker 负责。 USER §4 · 根 README §3.2
终端用户 无直接入口；GPU 不可用、加载失败或识别超时时，由 daemon 回退 CPU Final，Preview 不中断。 根 USER §4.4
  • worker 的 stdout 只承载协议帧；日志与诊断走 stderr，由 daemon 转发到 voime-log。
  • 协议不携带 segment_id、热键、目标或 Partial；这些属于 daemon 与前端 IPC。
