1. WHAT & WHY

↑

1.1 IDEAL：要解决的问题

FireRedASR2-AED 与 Qwen3-ASR 是两类不同的大模型，不能放进只加载 CPU ONNX Runtime 的 voimed。如果直接在主进程加载 GPU runtime，Vulkan / CUDA 会被迫进入 CPU 路径， GPU 崩溃也会带崩 SenseVoice Preview。Voime 把 GPU Final 隔离为两个模型专用 worker： voime-gpu-firered 加载 FireRed AED + FireRedPunc；voime-gpu-qwen3 加载 Qwen3-ASR。daemon 保留 SenseVoice、VAD、分段与 IPC，只把完整语音段交给当前 Final 对应的 worker。

1.2 GOAL：什么算成功

  • CPU daemon 不加载任何 GPU 库；只有 Final 选择 FireRed / Qwen 时才启动对应 worker。
  • 两个 worker 共用协议与生命周期，但各自独立编译、独立 runtime 包、独立测试。
  • worker 与 daemon 使用独立协议；GPU 崩溃、超时或显存不足不会中断 SenseVoice Preview。
  • GPU 只做 Final，不产生 Partial；所有 Partial 由常驻 SenseVoice 提供。
  • 两个模型都只接受 FP16；加载失败直接报错，不回退 FP32 或 int8。
  • Linux AMD 使用 Vulkan（P0）；Windows AMD 使用 Vulkan（P1）；NVIDIA 使用 CUDA（P1 / P2）。

1.3 非目标

  • 不做 VAD、分段、Preview、CPU ASR 或前端 IPC。
  • 不做 CPU 推理；不把 SenseVoice 搬进 worker。
  • 不引入 Python 运行时、云端 API、通用 ORT GPU EP、MIGraphX 或 DirectML。
  • 不做运行时插件 / 动态 EP 选择；两个 worker 是固定编译单元，由 daemon 按模型 kind 硬编码选择。
  • 不在 worker 内保存音频、历史或模型缓存；不联网。
  • 不通过重复运行非流式模型伪造 Partial。

2. 用户交互

↑

voime-gpu 没有终端用户界面；它的“用户”是 voimed 与打包 / 诊断脚本。 调用方通过 USER 的协议启动、请求、取消与关闭 worker。 两个 worker 的终端入口分别是 voime-gpu-firered 与 voime-gpu-qwen3。

调用方交互契约
voimed按 Final kind 选择 worker；spawn、Hello / Ready、Transcribe、Cancel、Shutdown；接收 Result / Error。USER §4.2 · voimed CORE §4.7
voime doctor通过 daemon 的 ListModels / BackendState 读取两个 backend 的 runtime、driver、VRAM 与当前 worker。voime USER §4.4

3. 边界

↑

拥有不拥有
FireRed worker：OpenASR / ggml Vulkan / CUDA；FireRed AED FP16 + FireRedPunc。CPU ONNX Runtime、VAD、SenseVoice、前端 IPC。
Qwen worker：llama.cpp / ggml Vulkan / CUDA；Qwen3-ASR 1.7B FP16 + mmproj。CPU ONNX Runtime、VAD、SenseVoice、前端 IPC。
worker 协议、handshake、取消、错误码、心跳；两个模型的 decode / 标点策略。前端 IPC、models/active、daemon 状态机、模型选择 UI。
worker 进程生命周期；由 daemon 监督。模型安装器、日志落盘、安装选项选择。
