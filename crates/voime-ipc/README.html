1. WHAT & WHY

↑

1.1 IDEAL：要解决的问题

daemon、TUI、Linux addon 与 Windows 前端使用不同语言与不同传输实现。如果每对客户端各自定义 消息结构，协议会随平台分叉，Partial / Final / segment_id 语义也会漂移。 voime-ipc 把线协议收敛为一个平台无关的库：消息类型、JSON 编码、换行 framing、 协议版本与错误码只在这里定义；它不包含 socket、pipe、线程或业务状态机。

1.2 GOAL：什么算成功

  • Rust 客户端与 C++ 前端使用同一组消息名、字段名与枚举值。
  • 一行一个 JSON；消息边界、最大长度、UTF-8 与版本规则明确。
  • daemon、TUI、Linux addon、Windows 前端对 Partial / Final / State 的解释一致。
  • 新增平台或前端不需要修改消息定义，只需要实现同一协议。
  • 协议变更必须提升 PROTOCOL_VERSION，旧客户端有明确错误或兼容路径。

1.3 非目标

  • 不实现 Unix socket、named pipe 或其他传输；传输契约属于 voime-transport。
  • 不实现 daemon 会话、角色冲突处理、广播或背压；这些属于 voimed。
  • 不处理热键、目标绑定、临时窗口或文本提交；这些属于平台前端。
  • 不保存历史、不加载模型、不访问文件系统。

2. 用户交互

↑

本库没有终端用户；它的“用户”是所有实现协议的客户端与 daemon。调用方通过 USER 中的类型与编解码函数发送 / 接收消息。

调用方交互契约
voimed解码 ClientMessage、编码 ServerMessage、按角色分发。USER §4 · voimed USER
voimeTUI / ctl / doctor 发送命令并读取快照与事件。voime USER §4
fcitx-addonC++ 侧用 nlohmann/json 实现同一消息集。fcitx-addon USER §4.3
frontends/windowsRust 前端直接依赖本 crate 的消息类型。windows USER §4.3
