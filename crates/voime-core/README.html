1. WHAT & WHY

↑

1.1 IDEAL：要解决的问题

语音识别链路包含音频设备、重采样、VAD、SenseVoice、Final 后端、标点与分段状态机。如果这些逻辑散落在 daemon、CLI 与平台前端里，跨平台适配会立刻产生多份 ASR / VAD / pipeline 维护成本。 voime-core 把这些平台无关的部分收敛为一个库：输入是 16 kHz 单声道 PCM， 输出是 PipelineEvent；不接触键盘、输入上下文、socket、pipe 或配置文件路径。

1.2 GOAL：什么算成功

  • Linux 与 Windows 使用同一份音频、VAD、SenseVoice、标点与 pipeline 代码。
  • voimed 只需要配置模型根目录、Final 目录、设备与线程数，就能获得 Partial / Final 事件。
  • 核心通过 FinalBackend 接受 CPU SenseVoice 或外部注入的 worker 后端，不直接依赖 GPU 库。
  • 模型清单是唯一的模型契约；启动时校验 SHA-256、张量与词表，运行期不重新加载权重。
  • 核心不依赖 Fcitx、Win32、Unix socket、named pipe、TUI 或 daemon 状态。
  • 分段、背压、Partial 节流与错误策略在同一套代码中实现，平台前端不复制识别逻辑。

1.3 非目标

  • 不解析命令行、不启动 daemon、不管理 socket / pipe。
  • 不处理热键、输入焦点、目标绑定、临时窗口或文本提交。
  • 不提供 TUI、配置 UI 或会话历史；这些属于 voime 与 voimed。
  • 不做模型下载、导出或安装；安装脚本在根 scripts/ / tools/。
  • 不加载 GPU runtime、不启动 worker；可选 voime-gpu 由 daemon 管理。
  • 不保存音频、按键或识别文本到磁盘。

2. 用户交互

↑

voime-core 没有直接的终端用户界面；它的“用户”是依赖它的软件。 调用方通过 USER 中的 Rust API 启动 pipeline、读取事件并关闭。

调用方交互契约
voimed构造 Config、启动音频与 pipeline、消费 PipelineEvent。USER §4
voime doctor读取默认模型根目录、active、Final 清单与音频设备列表。USER §4.1 · USER §4.2
根集成测试直接调用分段器、SenseVoice 解析与 pipeline 事件。CORE §5
