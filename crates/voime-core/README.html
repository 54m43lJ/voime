1. WHAT & WHY

↑

1.1 IDEAL：要解决的问题

语音输入的核心链路包含音频设备、重采样、VAD、预览与最终识别。如果这些逻辑散落在 daemon、CLI 与平台前端里，跨平台适配会立刻产生多份 VAD / ASR / pipeline 维护成本。 voime-core 把这些平台无关的部分收敛为一个 CPU 库：输入是 16 kHz 单声道 PCM， 输出是 Partial、完整语音段与 CPU Final 文本；不接触键盘、输入上下文、socket、pipe、 GPU runtime 或 daemon 状态。

1.2 GOAL：什么算成功

  • Linux 与 Windows 使用同一份音频、FireRedVAD、SenseVoice、Preview 与 CPU Final 代码。
  • voimed 只需要配置模型根目录、设备与线程数，就能获得 Partial 与完整语音段；CPU Final 由同一库提供。
  • 模型按一模型一目录加载：firered-vad 与 sensevoice-small 各自有 manifest、SHA-256 与 runtime 声明。
  • 核心不依赖 Fcitx、Win32、Unix socket、named pipe、GPU worker、TUI 或 daemon 状态。
  • VAD、Preview、CPU Final、分段、取消与背压在同一套代码中实现，平台前端不复制识别逻辑。
  • Final 触发后 Preview 立即停止并取消未开始的推理；cpu Final 只执行一次 SenseVoice 推理。
  • 最长语音段统一为 30 s，由分段器强制切分；模型 manifest 使用同一上限。

1.3 非目标

  • 不解析命令行、不启动 daemon、不管理 socket / pipe 或 Final 后端选择。
  • 不处理热键、输入焦点、目标绑定、临时窗口或文本提交。
  • 不提供 TUI、配置 UI 或会话历史；这些属于 voime 与 voimed。
  • 不做模型下载、导出或安装；安装脚本在根 scripts/ / tools/。
  • 不加载 GPU runtime、不管理 GPU worker、不执行 GPU Final。
  • 不加载独立标点模型；Qwen 的标点由 Qwen3-ASR 自身产生。
  • 不保存音频、按键或识别文本到磁盘。
  • 不负责设备选择策略、平台隐私 / 通信设备策略、平台路径、日志、systemd / 登录启动。
  • 产品级术语见 根 USER §1；核心内部约定见 本组件 CORE §2。
  • 模型目录、SenseVoice 与推理运行时的外部契约见 PROVIDER，不要在 README 或 USER 中复制张量形状。
  • GPU Final 由 voimed 调度到 voime-gpu-qwen3；核心只提供 CPU 路径。

2. 用户交互

↑

voime-core 没有直接的终端用户界面；它的“用户”是依赖它的软件。 调用方通过 USER 中的 Rust API 启动音频与 pipeline、读取事件、调用 CPU Final 并关闭。

调用方交互契约
voimed构造 Config、启动音频与 pipeline、消费 Recording / Partial / SegmentReady，在 Finalizing 调用 Final::transcribe。USER §4
voime doctor读取默认模型根目录、两个核心模型的 manifest 与音频设备列表。USER §4.1 · USER §4.2 · USER §4.3
根集成测试直接调用分段器、SenseVoice 解码与 pipeline 事件。CORE §5
  • 只装核心即可完成一次识别：VAD、Preview 与 CPU Final 都在本组件内。
  • GPU 模块不改变本组件的 API；voimed 只是决定是否把 SegmentReady 的 PCM 交给 worker。
