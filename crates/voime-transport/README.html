1. WHAT & WHY

↑

1.1 IDEAL：要解决的问题

daemon 与客户端需要本机传输：Linux 使用 Unix domain socket，Windows 使用 named pipe。 如果 socket / pipe 代码散落在 daemon、CLI 与前端中，跨平台适配会重复处理端点解析、权限、 阻塞 accept、关闭唤醒与错误映射。voime-transport 只收敛这些 OS 差异： 上层拿到统一的 Endpoint、Listener 与 Stream， 不关心底层是文件系统 socket 还是命名管道。

1.2 GOAL：什么算成功

  • Linux 与 Windows 的 daemon / CLI / Rust 前端只依赖同一套传输契约。
  • Unix socket 与 named pipe 各自原生实现，不强行共用一套 OS 调用。
  • 端点权限、陈旧端点处理、accept 取消与读写分离由 transport 负责。
  • 协议与消息完全不进入 transport；它只处理字节流与端点。
  • 传输 adapter 保持薄：不出现会话、分段、模型或业务分支。

1.3 非目标

  • 不定义 IPC 消息、JSON framing 或协议版本；这些属于 voime-ipc。
  • 不实现 daemon 会话、广播、背压或角色管理；这些属于 voimed。
  • 不追求“一套实现跑所有平台”；Unix 与 Windows 实现互不复用。
  • 不使用 loopback TCP 作为默认传输。
  • 不把 Endpoint 放进 voime-core::Config；端点不属于引擎。

2. 用户交互

↑

本组件没有终端用户；它的“用户”是 daemon、CLI 与 Rust 前端。调用方通过 USER 中的契约创建端点、bind / connect、accept 与关闭。

调用方交互契约
voimedbind(endpoint) 创建 listener，接受客户端流。USER §4.3 · voimed USER §4.4
voimeconnect(endpoint) 创建客户端流，读写 JSON lines。USER §4.3
frontends/windowsRust 托盘直接依赖本 crate 的 named pipe 客户端。windows USER §4.3
fcitx-addonC++ 前端不链接本 crate；按平台契约直接使用 Unix socket。fcitx-addon PROVIDER §4.5
