提案 — Voime 架构重做：CPU 核心 + 双 GPU Final 后端

README USER CORE PROVIDER ｜ 状态：待评审 · 未实现 · 2026-11-03

本文给出 Voime 下一次架构收敛的单一方案：核心安装是一个自带 CPU 推理、可独立工作的完整产品； GPU 推理作为可选模块单独安装，只负责最终文本识别。 核心固定使用 FireRedVAD 做 VAD、SenseVoice 做预览与 CPU Final；GPU 模块提供 FireRedASR2-AED + FireRedPunc（ORT + FP32 ONNX）与 Qwen3-ASR（llama-cpp-rs + BF16 GGUF） 两个可分别安装的 Final 后端。

本文按 clean rework 设计：不保留 CTC、CPU FireRedPunc、旧模型包布局、旧 models/active 指针与旧安装脚本的兼容层。升级按“重新安装核心 + 按需重新安装 GPU 模块” 处理；模型全部改为 ~/.local/share/voime/models/<model>/ 的一模型一目录布局。

1. 决策摘要

↑

决策点结论影响 / 边界
核心安装 独立、可用的 CPU 产品。包含 voimed、voime、平台前端、FireRedVAD、SenseVoice 与 ONNX Runtime CPU。 不安装 GPU 模块也能完成热键、VAD、预览、最终识别与提交；Linux 核心安装的 Fcitx5 addon 只允许 sudo 安装到 /usr 系统目录。

Preview 固定由核心的 SenseVoice 提供。Final 触发后不再产生新的 Partial，并停止 / 取消 Preview 的 CPU 推理。 GPU 后端不接收 Partial、不参与预览；预览渲染属于核心安装（平台前端），GPU 模块不含前端代码。
CPU Final SenseVoice 同时是默认 Final 与 GPU 失败回退。 只装核心即可最终上屏；GPU 不可用时不阻塞产品主路径。
GPU 模块 可选、Final-only、独立进程。两个 worker：voime-gpu-firered 与 voime-gpu-qwen3，各自独立 crate / 二进制 / runtime。 GPU 只接收完整语音段；不加载 VAD、不产生 Partial、不接管前端；同一时刻只运行一个 Final 后端。

模型存储 一个模型一个目录：~/.local/share/voime/models/<model>/。 不再有“模型包 = 一个 backend 大目录”和 models/active 指针；每个目录自包含 manifest 与权重。
安装入口 两个脚本：核心安装脚本 + GPU 推理模块安装脚本。 GPU 脚本默认安装两个后端（FireRed 组合 + Qwen），但 final.backend 仍保持 cpu；--firered / --qwen3 选择性安装，--backend 显式切换。
Final 后端选择 默认 cpu，安装 GPU 不自动切换。通过 --backend 或 voime ctl backend 显式指定 firered / qwen3；运行中切换需重启 daemon。 切换只影响 Final；Preview 始终 SenseVoice。默认值、安装选项与切换入口见 §10。
兼容策略 运行期不兼容旧格式。旧 CTC、CPU Punc、旧 manifest、旧模型包与旧安装脚本一律拒绝。 升级 = 重装核心 + 按需重装 GPU 模块；不提供运行期迁移层。
  • “核心安装”不是只有库：它包含 daemon、CLI、平台前端与 CPU 模型，用户只装核心就能使用完整语音输入。
  • “GPU 模块”不是新的产品入口：它只增加 Final 识别能力，不改变热键、目标、预览与提交语义。
  • 本文的“Final”指完整语音段结束后用于提交的一行文本；“Preview”指录音期间显示但永不提交的临时文本。

2. 目标、非目标与设计边界

↑

2.1 目标

  • 核心安装开箱可用：无 GPU、无网络、无 Python 也能完成 VAD、预览与最终识别。
  • 核心固定 FireRedVAD 与 SenseVoice，VAD 与 Preview 不被任何后端替换。
  • GPU 模块只做 Final，两个后端可以分别安装、分别升级、分别卸载。
  • FireRed 后端以 FireRedASR2-AED 负责识别、FireRedPunc 负责标点；Qwen 后端只加载 Qwen3-ASR 的 BF16 GGUF 主模型与 BF16 mmproj。
  • FireRed 使用上游现成 FP32 ONNX；Qwen 使用上游现成 BF16 GGUF；不在用户机器上做模型转换或量化。
  • 模型按“一模型一目录”存放，安装脚本与运行期共用同一套目录与 manifest 校验。
  • 安装入口收敛为两个脚本；GPU 脚本默认装两个后端，也支持只装其中一个。
  • GPU 崩溃、驱动缺失、显存不足或模型缺失时，核心 Preview 与 CPU Final 仍然可用。

2.2 非目标

  • 不做 GPU VAD、GPU Preview、GPU Partial 或流式 GPU 识别。
  • 不做 CPU FireRedASR2-AED / CPU Qwen3-ASR；GPU 失败不加载任何 CPU 大模型。
  • FireRed 不引入 GGUF / llama.cpp / OpenASR；Qwen 不引入 ONNX / ORT GPU；AMD Linux 的 Qwen 只提供 Vulkan，不构建或发布 HIP / ROCm runtime。
  • 不做运行期模型转换、量化、导出或下载；这些只发生在安装脚本与发布流程。
  • 不做两个 GPU 后端同时推理；安装可以并存，运行期只选择一个 Final。
  • 不做模型目录自动发现、动态插件或通用 backend ABI；两个 worker 是固定构建单元。
  • 不做文本润色、纠错、翻译、摘要或规则后处理；Final 只做 ASR（FireRed 额外做标点）。
  • 不做旧 CTC / 旧 Punc / 旧模型包 / 旧 active 的兼容与迁移。

2.3 设计边界

约束对方案的要求
核心必须独立可用 核心安装不得依赖 GPU 库、GPU 模型或 GPU worker；只装核心时必须能完成一次完整识别。
VAD 与 Preview 不可替换 所有模式共用 FireRedVAD；Preview 只由 SenseVoice 产生；GPU worker 不接触活动段音频。
音频线程不能被推理阻塞 VAD、Preview、Final 都在 pipeline 工作线程串行执行；GPU 调用必须有超时、背压与回退。
核心不加载 GPU 运行时 核心二进制不链接 CUDA / MIGraphX / DirectML / Vulkan；GPU 库只存在于 worker 的独立目录。
模型只读、运行期不联网 模型由安装脚本写入；启动时校验 SHA-256 与张量；运行期不下载、不改写、不记录识别文本。
一个语音段一个 Final Final 触发后 Preview 停止；同一段只能有一个 Final 或一次显式丢弃，不允许并行 Final。
模型版本与运行时解耦 模型目录只放权重与配置；FireRed 的 ORT GPU runtime 与 Qwen 的 llama.cpp runtime 分别由 GPU 安装脚本管理，互不覆盖。

3. 目标架构

↑

核心安装与 GPU 推理模块是两个独立的安装单元，但只有一个产品入口。核心持有音频、VAD、Preview、 分段、会话与前端 IPC；GPU 模块只提供一组受控的 Final 识别 worker。

  • 核心安装包含平台前端；Linux 上是 Fcitx5 addon，Windows 上是托盘 / 前台前端。

  • 两个 worker 共用 voime-gpu-common 的帧协议，但各自链接不同的 runtime：FireRed 只链 ORT，Qwen 只链 llama.cpp。
  • 核心不链接 GPU runtime；worker 不加载 VAD、不产生 Partial、不接触前端 IPC。

4. 核心 CPU 路径

↑

核心安装内部的路径不区分是否安装 GPU：音频始终经过同一套采集、VAD、分段与 Preview。 只有 Final 阶段由 voimed 根据 final.backend 选择 CPU SenseVoice 或某个 GPU worker； voime-core 不感知后端选择，只提供 Preview 取消接口与 CPU Final。

5. GPU 推理模块

↑

GPU 模块只解决“最终文本识别”。它是一个可独立安装的 worker 集合，不是新的 daemon，也不是前端插件。 核心通过本机进程协议把完整语音段交给 worker，worker 只返回文本与耗时。

5.1 边界

项目契约
输入完整语音段 PCM：16 kHz、单声道、f32；一次请求一个段。
输出最终文本（FireRed 已加标点；Qwen 保留自带标点 / 大小写）与耗时。
不接收活动段增量音频、VAD 状态、Partial 请求、前端 IPC、热键 / 目标。
不产生Partial、VAD 判定、分段、预览渲染、会话历史。
并发同一 worker 一次只处理一个 Final；daemon 不在上一段未完成时发下一段。

  • 两个后端可同时安装，但运行期只启动 final.backend 选中的一个；另一个不占显存。
  • FireRedPunc 只存在于 FireRed worker，不进入核心；Qwen 不加载 FireRedPunc。
  • Qwen 的 mmproj 是同一模型的音频投影器，不是第二个 ASR / 标点模型；Qwen 后端仍然只装 Qwen3-ASR 这一套模型。

  • GPU 后端不是“可替换的 VAD / Preview”：替换 Final 不改变任何 Preview 行为。

5.3 worker 协议

两个 worker 共用一套帧协议：控制消息用 JSON，音频用原始 little-endian f32 PCM； 每帧带长度前缀，避免 base64 与文本编码开销。 

Frame
├── u32 header_len
├── header: UTF-8 JSON
├── u32 audio_len
└── audio: f32le mono, 16 kHz, [-1, 1]

Request
├── Hello { protocol, backend, model_dir, device }
├── Transcribe { id, sample_rate, language }
├── Cancel { id }
└── Shutdown

Response
├── Ready { protocol, backend, runtime, device, vram_mb, punc }
├── Result { id, text, latency_ms, rtf }
├── Error { id, code, message }
└── Bye
错误码含义daemon 动作
RuntimeMissingGPU runtime / backend 未安装或版本不匹配。标记后端不可用；Final 回退 CPU；提示重装 GPU 模块。
DeviceUnavailable无 GPU、驱动不匹配、显存不足。不启动 worker；Final 回退 CPU；doctor 报原因。

InferenceFailed运行期推理失败。当前段回退 CPU；重启 worker；连续失败标记不可用。

ProtocolMismatchworker 与 daemon 协议版本不一致。拒绝 worker；提示重装 GPU 模块。
  • 协议字段为提案草案；最终字段、版本与错误码以 voime-gpu-common USER 为准。
  • FireRed worker 不切换 EP / runtime；RuntimeMissing / DeviceUnavailable / LoadFailed 均使 FireRed 后端不可用，只有 daemon 按 §10.5 对当前段回退 CPU SenseVoice。
  • Qwen 的 mmproj 路径由模型 manifest 声明；worker 只接受模型目录，不从全局配置或环境变量猜路径。
  • worker 的 stdout 只用于协议；日志走 stderr，由 daemon 转发到 voime-log。
  • 协议不记录识别文本；daemon 只记录长度、耗时、错误码与后端名称。
  • worker 协议独立于前端 IPC，不提升 voime-ipc 的协议版本。

5.4 worker 生命周期

阶段行为超时 / 失败

5.5 运行时隔离与冲突核查

结论：Qwen3-ASR 用 BF16 GGUF + llama.cpp 可行，且与 FireRed 的 ORT / ONNX 路径不冲突—— 前提是后端按 crate、二进制、进程、runtime 目录四层拆开。 这不是“两个库碰巧能一起跑”，而是用结构保证它们不在同一个地址空间、同一个链接单元、 同一个动态库目录里相遇。

核查项结论依据 / 约束
Qwen BF16 模型 可用 ggml-org/Qwen3-ASR-1.7B-GGUF 同时提供 BF16 主模型（约 4.07 GB）与 BF16 mmproj（约 642 MB）；音频输入优先使用同版本 BF16 mmproj，Q8 mmproj 不作为产品路径（已有导出者报告质量退化）。
llama.cpp 支持 可用 Qwen3-ASR 已于 2026-04 合入 llama.cpp；官方 GGUF 可以直接由 llama-mtmd-cli / llama-server 加载。音频输入仍标 experimental，需锁定版本并做金样。
Rust 绑定 可用 llama-cpp-rs 项目当前发布 crate llama-cpp-4 0.11.0；mtmd feature 提供 MtmdBitmap::from_audio(&[f32])、MtmdCapabilities.audio、MtmdContext::tokenize 与 eval_chunks，可以直接吃核心传来的 PCM，不需要临时 WAV。
BF16 运行 有条件 llama.cpp / GGML 支持 BF16；Vulkan 设备需报告 bf16: 1，否则该设备不能走 BF16 加速。必须在开发前于目标 GPU 上实测；不支持的设备按 §10.5 回退 CPU。
运行时符号冲突 不冲突 两个 worker 是不同二进制 / 进程：FireRed 只链接 ORT，Qwen 只链接 llama.cpp。不要把两个后端放进同一个 crate 同时开启两套 feature——Cargo 的 feature 合并可能让两个二进制都链接两套 runtime。
显存冲突 可控 daemon 一次只启动一个 worker；切换时先停旧 worker 并等待显存释放。两个 worker 同时运行会争抢 VRAM，不支持。
库版本冲突 可控 ORT GPU runtime 与 llama.cpp runtime 各放独立目录，worker 各自设置 rpath / 库路径；不写全局 LD_LIBRARY_PATH，不共享打包的 CUDA / cuDNN / Vulkan runtime 目录（系统驱动与 Vulkan loader 可共享）。
核心隔离 保持 核心只链接 CPU ORT；不依赖任一 GPU worker crate，也不加载 GPU 库。

AMD Linux 的 Qwen backend 固定 Vulkan。 不构建、不安装、不发布 HIP / ROCm runtime，也不在安装脚本中暴露 hip 选项。 Vulkan 使用系统 Vulkan loader 与 GPU 驱动，不引入 ROCm 栈；这与“核心安装不依赖 GPU runtime、GPU 后端独立”的边界一致。

  • Vulkan 在 RDNA 4 上也有模型形状相关的性能回退报告；Qwen3-ASR 1.7B 必须在目标机器上用实际 30 s 段验证，不能只看 8B 文本模型 benchmark。
  • 本决定只约束 Qwen / llama.cpp：AMD Linux 只发 Vulkan。FireRed 仍走 ORT GPU EP；其 AMD Linux 路径依赖 MIGraphX / ROCm。若要求整个产品都不引入 ROCm，FireRed 在 AMD Linux 必须标为不可用，只保留 NVIDIA CUDA 与 Windows DirectML。

9. 风险

↑

风险影响缓解
FireRed 的 ORT GPU EP 与目标硬件不匹配AMD Linux 需要 MIGraphX / ROCm，部署复杂；CUDA 只覆盖 NVIDIA。准备阶段先验证发行版 onnxruntime 包；不可用则源码编译支持 MIGraphX 的 runtime；ort 用 api-29 + load-dynamic；Qwen 的 Vulkan 路径可作为 AMD Linux 的先行后端。
FireRed runtime 无可行部署无法加载 MIGraphX provider 时 FireRed 后端不可用，安装时间与构建依赖不可接受。准备阶段先验证发行版 onnxruntime 包；不可用则在安装 GPU 后端时源码编译支持 MIGraphX 的 runtime；仍不可行则取消 FireRed 后端。
系统 ORT 1.29 与 ort API 版本不匹配ort 默认 API 31，直接加载 1.29 可能失败或运行期崩溃。FireRed worker 固定 default-features=false + api-29 + load-dynamic + migraphx；启动时校验 ORT 版本与 MIGraphX provider。
Arch onnxruntime-rocm 与系统 onnxruntime 冲突安装包互相冲突，可能影响用户其他应用。核心使用私有 CPU ORT；准备阶段决定使用发行版包还是源码 runtime；不强制卸载系统 CPU ORT。
Qwen BF16 在目标 GPU 上不可用Vulkan 设备可能报告 bf16: 0；此时 BF16 不能作为加速路径，性能或可用性下降。worker 启动时自检 BF16；doctor 只报 worker ready / running；不支持的设备按 §10.5 回退 CPU。
llama.cpp 音频仍是 experimental输出质量、长音频、版本升级可能回归；Qwen3-ASR 输出可能带 asr_text 包装。锁定 llama.cpp commit / crate 版本；30 s 分段规避长音频问题；worker 清洗包装；目标语料金样。
llama-cpp-4 绑定较新API 变动、与 llama.cpp 版本错配、构建失败。固定 crate 版本与对应 llama.cpp commit；worker 内封装 mtmd 调用；升级必须重跑金样。
两个 GPU runtime 被错误地放进同一个 crate / 二进制Cargo feature 合并可能让同一二进制链接 ORT 与 llama.cpp，引入符号、CUDA / Vulkan 或库版本冲突。拆成 voime-gpu-common + 两个独立 backend crate；每个 worker 只开自己的 feature；CI 检查动态依赖。
第三方 FireRed ONNX 导出质量 / 维护导出包可能变更、下架或 tokenizer 不匹配。固定 revision + SHA；发布时镜像模型包；开发前对照官方输出做金样。
FireRedPunc ONNX 词表 / 标签不一致标点错位、漏标或加错标点。固定导出包与 tokenizer；对官方样例做金样；失败不返回半成品文本。
GPU 崩溃 / 驱动重置Final 失败，甚至影响桌面。worker 独立进程 + 超时 + 回退 CPU；不在核心进程加载 GPU 库；切换后端先停旧 worker。
安装体积大默认两个 GPU 后端约 9.6 GB，下载时间长。脚本显示体积；支持选择性安装、断点续传、离线源；核心安装保持小体积。
ORT / llama.cpp 版本漂移协议不兼容或库冲突。核心、FireRed、Qwen 各自带 runtime；worker 协议带版本；发布时锁定版本矩阵。
Finalizing 期间 Preview 推理未取消CPU 资源浪费、Final 延迟增加，违背 10.6 的节省计算目标。Preview 调度器使用取消令牌 / Finalizing 门禁；测试统计 SenseVoice 调用次数；GPU Final 期间为 0，CPU Final 只 1 次。
Preview 与 Final 文本差异用户看到临时文本与最终文本不同。产品接受该差异；Final 才提交；Preview 中断后不再更新，避免“最终文本被预览覆盖”的错觉。
Fcitx addon 需要提权 / 系统路径用户级安装需扩大 Fcitx 库搜索面，安全边界不可接受；拒绝 sudo 时 addon 无法安装。只允许 sudo 安装到系统 addon 目录；核心其余文件用户级；安装脚本只对 addon 步骤提权；--no-addon 可跳过；doctor 检查系统路径与 ABI。

#决策点结论影响
10.1 平台与 runtime A. Linux + AMD 为验收基线：Qwen 用 Vulkan，FireRed 用 ORT MIGraphX。Windows 与 Linux 其他 GPU 组合按 §5.5 支持矩阵实现。 Qwen 不构建、不安装 ROCm / HIP；FireRed 的 AMD 路径依赖 MIGraphX / ROCm；开发前准备在 AMD 机器验收。
10.2 Qwen3-ASR 规格 A. Qwen3-ASR 1.7B BF16 主模型 + BF16 mmproj（约 4.1 GB + 0.6 GB）。 Qwen 显存门禁按 8 GB 设计；模型目录 qwen3-asr-1.7b；不提供 0.6B 默认包。
10.3 Final 后端默认值 B + C. 默认 cpu；安装 GPU 不自动切换；install-gpu.sh --backend 或 voime ctl backend 显式指定；运行中切换需重启 daemon。voimed 不提供 --backend 选项。 安装脚本、README、USER、voime ctl 文档按“默认 CPU、显式 GPU”写；不提供 IPC 热切换。
10.4 GPU worker 生命周期 A. daemon 启动时加载选中的 GPU worker 并常驻；默认 cpu 时不启动 worker。 首段 Final 延迟稳定；Qwen 常驻显存；切换后端通过重启 daemon 生效。
10.5 GPU 失败回退 A. 当前段自动回退 CPU SenseVoice；Preview 不中断。 worker 加载失败、超时、崩溃、显存不足均走该路径；记录错误码与后端名，不记录文本。
10.6 Finalizing 期间预览 A. 保留最后一条 Partial 直到 Final；Finalizing 期间停止并取消 Preview 的 CPU 推理；cpu Final 只执行一次 CPU 推理，GPU Final 不再调用 SenseVoice。 Preview 调度器必须有取消 / 门禁；测试统计 SenseVoice 调用次数；这是节省计算资源的硬约束。
10.7 Fcitx addon 安装位置 只允许系统级安装：申请 sudo 写入 /usr 系统 addon 目录与 /usr/share/fcitx5/addon；不读取用户目录，不设置 FCITX_ADDON_DIRS。核心其他文件仍保持用户级。 fcitx 文档只写系统安装与 sudo；--no-addon 可跳过；安装 / 卸载 addon 需要提权，失败不静默降级为用户目录。 doctor 检查系统路径与 ABI。
10.8 平台覆盖 A. Linux 与 Windows 使用同一套核心 / GPU 架构：Linux 验收基线为 AMD + MIGraphX / Vulkan；Windows 使用 FireRed DirectML、Qwen Vulkan / CUDA，安装入口为 install-core.ps1 / install-gpu.ps1；TSF 为可选前端。 Windows 文档与 Linux 同等完整；产品文档不出现平台时序措辞。
10.9 FireRedPunc ONNX 来源 A. 采用现成第三方 ONNX 导出，固定 revision 与 SHA-256；验证 tokenizer、标签与许可证。 FireRedPunc 模型目录、安装源与金样按该导出包写；不自行训练或转换。
10.10 模型目录命名 A. 固定目录名 + manifest 版本；不把版本号拼进目录名。 模型升级只替换目录内容并更新 manifest；配置路径不变。
10.11 最长语音段 A. 30 s 强制切分。 核心分段上限、模型 manifest 与长段测试统一为 30 s；超长语音由 VAD / 分段器继续切分。
10.12 模型下载 / 运行期失败 模型下载失败：安装脚本报错退出，不留下半成品目录；运行期失败：按 10.5 回退 CPU。 安装脚本非零退出并清理临时目录；运行期不因模型缺失阻塞核心；doctor 给出修复命令。
10.13 FireRed runtime 部署 准备阶段调研并冻结：先验证发行版 onnxruntime 包是否包含 MIGraphX；不可用则在安装 GPU 后端时源码编译支持 MIGraphX 的 runtime；没有可行方案则取消 FireRed 后端。 ort 固定 api-29 + load-dynamic + migraphx；运行期不切换 EP / runtime；发行版包名与源码构建参数由准备阶段记录。
  • 10.6 是硬约束：Finalizing 期间只允许一次 Final 推理，不得继续为 Preview 跑 CPU；实现需要取消令牌 + 调用计数测试。
  • 10.7 不再采用用户级 addon 加载：Fcitx 默认只搜索系统 addon 库目录；把用户目录加入 FCITX_ADDON_DIRS 会扩大库搜索面，已否决。addon 只允许 sudo 安装到系统目录。
  • 10.8 的 Windows 是完整目标平台，文档按同一架构定义；不使用“本轮 / 后续”等时序措辞。
  • 10.13 准备阶段先验证 Arch 官方 onnxruntime-rocm 1.29.0：包内已含 libonnxruntime_providers_migraphx.so；不可用则源码编译，第三方预编译不作为产品路径。
