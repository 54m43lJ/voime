提案 — ASR v2：SenseVoice 收敛与 GPU 后端

README USER CORE PROVIDER BUILD ｜ 状态：待评审 · 未实现 · 2026-11-01

本文给出 ASR 的单一决策：删除 CTC、保留 SenseVoice ITN、删除 SenseVoice + Punc 变体、 删除 AED CPU 推理、否决文本后处理、增加可选 voime-gpu；VAD 保持现状，不纳入本提案。 文档同时定义 SenseVoice Preview / Final 分工、音频预卷、CPU / GPU 推理契约、安装档位、模型包切换与验收门禁。

本文按 clean break 设计：运行期不承诺旧 schema、旧模型包、旧 active / legacy 布局、 旧前端协议兼容，也不建立兼容层。升级默认按“重新安装新版本 + 新模型包”处理； 另提供一个独立、可选、一次性的迁移脚本，由用户自行决定是否运行，它不属于安装脚本。 运行期失败回滚仍然保留，但它只回滚到本次运行已经加载的新 pipeline，不涉及旧版本迁移。

结论先行：实际使用中没有观察到 SenseVoice 的明显错别字；此前少量字符差异更可能来自已删除的 CTC 路径， 而不是 SenseVoice 模型。本文不再展开 LFR 边缘处理、量化精度与语言参数的归因， 确定保留的改进只有分段音频预卷；另做一个受控的 Rust ort 版本实验，有实际收益才采纳。 SenseVoice 保持当前推理路径，不换模型、不改前端。

2. 目标、非目标与设计边界

↑

2.1 目标

  • 保留 SenseVoice 作为常驻 Preview 后端与 CPU Final 默认；删除 CTC、SenseVoice-punc 与 AED CPU 路径。
  • 确定保留的 SenseVoice 改进是分段音频预卷，用于修复段首缺字；另做一次受控的 Rust ort 版本实验，有实际收益才采纳。
  • 增加可选 voime-gpu：只用于 Final；Preview 始终由 SenseVoice 处理，CPU 路径不加载任何 GPU 库。
  • 保留包级切换：models/active 只选择 Final 模型；切换不需要重装 SenseVoice 或替换二进制。
  • 安装档位两选一：sensevoice 只装一个模型；firered 安装 SenseVoice + FireRed 两个模型。
  • 复用现有 VAD、分段、音频采集、IPC、前端提交与 ONNX Runtime 边界。
  • 失败可回滚：新 Final 加载或推理失败时恢复旧 Final；GPU 不可用时 Final 回退 CPU SenseVoice，Preview 不受影响。

2.2 非目标

  • 不做运行时双模型热切换，也不在录音 / 识别过程中切换 Final 后端。
  • 不做 CPU AED；GPU 失败不自动加载 AED CPU。
  • 不做 GPU Partial：Preview 固定由常驻 SenseVoice 产生，voime-gpu 只接收完整语音段做 Final。
  • 除受控的 Rust ort 版本实验外，不改 CPU SenseVoice 的 LFR / fbank / CMVN / 量化 / 语言参数；预卷是唯一确定改动。
  • 不更换、不调优、不评测 VAD：继续使用现有 FireRedVAD、模型与阈值；分段预卷只改变 ASR 输入窗口。
  • 不实现文本后处理：不增加规则层、文本纠错模型、--rewrite、清单字段或 IPC 消息。
  • 不引入第二推理引擎、Python 运行时、云端 API 或 GPU 依赖到 CPU daemon。
  • 第一批不接 LLM；低于 FireRed AED 精度的 LLM 不测试。
  • 运行期不承诺旧 schema、旧模型包、旧目录布局或旧前端协议兼容；只提供一个独立、可选的一次性迁移脚本，不把迁移纳入安装流程。
  • 不做模型微调、领域自适应训练或通用文本润色。
  • 不把 SenseVoice 的语言 / 情感 / 事件标签暴露给前端；一期只消费文本。

2.3 设计边界

现有约束对新方案的要求
pipeline 只有一个工作线程，VAD / ASR / 标点串行 推理不能进入音频回调线程；新增阶段必须有明确预算，不能靠异步运行时规避串行成本。
音频通道与完成段队列有界，满时丢弃 voime-gpu 超时、模型加载失败与后端重启都必须有背压与回退策略，不能拖垮 Continuous。
模型清单是唯一契约；SHA-256、张量、词表都在启动时校验 CPU / GPU 包都通过同一份清单校验；worker 加载时再次校验自己的产物。
运行期不联网、模型只读、日志不记录识别文本 voime-gpu 协议只回传结果；daemon 只记录长度、耗时与错误码。
CPU 直接使用 ort，不链接 sherpa-onnx 运行时 SenseVoice / AED 的预处理、LFR、CMVN、特殊 token 与自回归解码都在项目内实现。
Linux 用 systemd，Windows 用托盘托管 daemon “重启后端”是 daemon 内部重建 pipeline，不依赖 systemd / 托盘重启进程。

SenseVoice 常驻；GPU Final 可选 SenseVoice 始终加载，负责全部 Preview 与 CPU Final；只有 Final 选择 FireRed 时才加载 voime-gpu。同一时刻只有一个 Final 后端，但 Preview 与 GPU Final 可以并存。
  • 这些边界是后续设计的前提；违反其中任何一条，都会把 CPU 路径、GPU 隔离或切换语义重新打开。
  • “单后端”现在指“单 Final 后端”；SenseVoice Preview 是常驻基础路径，不计入 Final 的并行加载。

3. 任务一：音频预卷与 ORT 版本实验

↑

3.1 结论与范围

实际使用中没有观察到 SenseVoice 的明显错别字；此前少量字符差异更可能来自已删除的 CTC 路径， 而不是 SenseVoice 模型。因此本提案不再展开 LFR 边缘处理、量化精度与语言参数的归因或改动， SenseVoice 保持当前推理路径。

确定保留的改进是分段音频预卷：它不改变模型、不改变 VAD 判定，只修复交给 ASR 的音频窗口， 用于减少段首辅音 / 爆破音被切掉造成的缺字或近音替换。它的收益直接、风险最低，且与 CTC / SenseVoice 的模型选择无关。

另外保留一个受控的 ORT 版本实验：只比较当前 CPU ORT 与候选稳定版本；在目标语料上看到实际收益才采纳， 看不到收益就保持当前版本并关闭实验。它不是“框架对齐”工程，不扩展到 LFR、fbank、量化或语言参数。

3.2 当前行为与问题

当前 Segmenter 从“第一个被 VAD 判为语音的帧”开始收集音频，没有保留语音起点之前的音频。 FireRedVAD 的流式参考配置包含 pad_start_frame=5（约 50 ms），而项目当前没有实现这个预卷； 中文的塞音 / 擦音起始、英文的爆破音很容易被切掉，表现为段首缺字或近音替换。

3.3 改进方案

  • Segmenter 维护一个短环形缓冲，默认回取 200–300 ms；VAD 判定与端点参数保持不变。
  • PTT / Toggle：按键按下即开始缓冲，预卷成本最低。
  • Continuous：常驻环形缓冲，按帧回取；只改变交给 ASR 的音频范围。
  • 预卷长度按目标语料调整；过长会把前一段尾音带进来，建议从 200 ms 起测。
  • 不引入后卷、平滑、阈值调整或 VAD 替换；这些不在本提案范围内。

3.5 Rust ort / ONNX Runtime 版本实验（条件项）

Rust 侧默认构建下，ort crate 版本决定绑定的 ONNX Runtime 版本；不通过 load-dynamic 混搭任意 runtime。 当前 POC 使用 ort 2.0.0-rc.12 / ONNX Runtime 1.24.2；可选的稳定路径有限： ort 2.0.0-rc.13（ONNX Runtime 1.28）与 ort 2.0.0-rc.15（ONNX Runtime 1.31； rc.14 同为 1.31，不单独测）。 实验实际是一次 ort 依赖升级，只比较这几个版本；如果项目 MSRV 或 API 约束导致无法升级， 就直接关闭实验，不做其它运行时替换。

项目约定
对照ort 2.0.0-rc.12 / ORT 1.24.2（当前） vs rc.13 / ORT 1.28 vs rc.15 / ORT 1.31；以实际可编译、MSRV 允许的版本为准。
变量只改 ort crate 版本及其 API 适配；模型、fbank、LFR、CMVN、量化、语言参数、解码与分段策略全部保持一致。
指标目标语料 CER / 替换错误率；p95 收尾延迟；峰值 RSS；加载时间；失败率。
采纳门槛CER 或替换错误率有统计显著改善，且延迟 / 内存不退化；否则保持 rc.12 / ORT 1.24.2。
不做什么不做多版本长期矩阵；不引入第二推理引擎；不用 load-dynamic 混搭任意 runtime；不为 ORT 版本改模型、前端或分段策略；没有可选版本就不做。
  • 这是条件实验，不是必须落地的改进；没有收益或没有可选版本就记录结论并关闭，不进入后续阶段。
  • 如果采纳，固定新版本、build info 与 API 适配，并重跑 SenseVoice 回归；如果不采纳，保留当前版本与现有构建配置。

3.6 不在本提案中的改动

  • 除 §3.5 的 ORT 版本实验外，不调整 CPU SenseVoice 的会话配置、图优化级别或执行提供者；voime-gpu 的 ORT / EP 属于第 5 节。
  • 不切换 LFR 边缘处理，不改 fbank / CMVN 数值。
  • 不做 int8 / fp32、language=auto / zh 的对照或调参。
  • 不评估 Paraformer / Whisper 等 CPU 替代模型；SenseVoice 继续作为唯一 CPU 默认后端。
  • 不把 CTC 的识别问题归因到 SenseVoice；CTC 按 §6.2 删除。

4. 目标架构：CPU daemon + 可选 voime-gpu

↑

SenseVoice、VAD 与 Preview 路径始终留在 voimed / voime-core 内，使用 CPU-only ORT。 GPU 只作为可选 Final 能力：只有 active 选择 FireRed 时才拉起独立的 voime-gpu 进程； 所有 Partial 仍由常驻 SenseVoice 处理。这样 CPU 路径不增加额外进程，GPU 也不污染 Preview 与 CPU 路径。

  • voimed / voime-core 使用 CPU-only ORT；不加载 GPU 库。
  • SenseVoice 始终加载：所有 Partial 与 CPU Final 都由它处理。
  • voime-gpu 是唯一加载 DirectML / MIGraphX / CUDA 的进程，只在 Final 选择 FireRed 时启动；它不处理 Partial。
  • VAD 与 FireRedPunc 始终在 daemon 的 CPU ORT 上；GPU Final 模式下也不搬进 worker。
  • Final 选择 CPU SenseVoice 时 worker 不启动；切换回 CPU Final 时停掉 worker 并释放显存，SenseVoice Preview 不中断。
组件职责不负责
voimed 音频采集 / 重采样、环形缓冲、分段、前端 IPC、目标注入、Final 模型选择、voime-gpu 生命周期。 GPU 库、GPU 会话、具体 GPU 模型解码。
voime-core CPU-only ORT；FireRedVAD、常驻 SenseVoice（Preview + CPU Final）、FireRedPunc（GPU Final）；fbank / LFR / CMVN；Partial / Final 文本。 GPU 模型、GPU EP、前端 IPC、目标注入。
voime-gpu GPU-only ORT；FireRed AED FP16 Final；返回原始文本与耗时。 VAD、分段、Preview、标点、CPU ASR、前端 IPC。
模型包 SenseVoice 基础包 + 可选 FireRed Final 包；权重、清单、SHA、VAD / Punc。 不包含运行时库、不写日志、不联网。
GPU runtime 包 按 OS + EP 拆分的 voime-gpu runtime 包；可选安装。 不进入模型目录，不被 active 直接选择。

  • daemon / voime-core 不创建 GPU 会话；GPU 包的文件、SHA、张量由 worker 在加载时校验。

4.5.1 为什么重启后端而不是重启进程

“重启后端”只替换 daemon 内的 Final 配置 / Final 后端 / voime-gpu；SenseVoice Preview 常驻， 既不退出 voimed，也不经过 systemd / 托盘。这个边界来自变更范围：Final 切换只改变最终识别模型， 不改变 Preview、IPC 端点、前端连接、会话历史、日志、权限与进程生命周期。 把进程一起重启，会把一次“换 Final”扩大成“重启整个服务”，带来不必要的状态丢失、重连与失败恢复问题。

  • 判断标准不是“哪种重启更简单”，而是“变更影响到哪一层”：只影响 pipeline 就只重建 pipeline。
  • 内部重启把复杂度留在 daemon（可替换字段、显式 shutdown、回滚），避免把复杂度推给两个平台前端与进程管理器。
  • 保留进程级重启作为兜底，不把它作为日常模型切换路径。

5.2 方案比较

方案收益代价 / 风险结论
A. 在 daemon 内直接使用 ORT GPU EP 实现最短；复用 SessionFactory。 GPU 库进入 daemon；CPU 路径无法保证不加载；GPU 崩溃带崩 daemon。 不采用。
B. 可选 voime-gpu 进程（仅 Final） CPU daemon 只带 CPU ORT；SenseVoice Preview 常驻；GPU 库只在 worker；崩溃隔离；可按需启动 / 停止。 需要协议、生命周期、超时与安全校验；多一个进程（仅 GPU 模式）。 采用。
C. CPU / GPU 两个 runtime 进程 CPU 推理也完全独立。 VAD / Punc 本来就要常驻；再拆一个 CPU 进程增加 IPC、生命周期与重复模型，收益不足。 不采用。
D. 动态库插件 调用开销低。 插件与 daemon 同进程；GPU 崩溃 / 库版本仍带崩 daemon。 不采用。
E. 外部推理服务器 吞吐高；LLM 生态成熟。 Python / CUDA 依赖重；启动慢；桌面安装复杂。 只做离线评测。

5.6.1 CPU / GPU 运行时隔离

硬规则：CPU daemon（voimed / voime-core）只加载 CPU ORT；voime-gpu 是唯一允许加载 GPU ORT / EP 库的进程。 只要把 GPU EP 编进 daemon，就无法保证 CPU 推理不碰 ROCm / CUDA / DirectML。

路径进程ORT 构建模型加载 GPU 库
SenseVoice CPU voimed / voime-core ORT CPU only SenseVoice int8（Preview + CPU Final）+ VAD 否
FireRed AED GPU voime-gpu DirectML / MIGraphX FireRed AED FP16 是，仅 worker
VAD / Punc（GPU 模式下） voimed / voime-core ORT CPU only FireRedVAD + FireRedPunc 否
  • 基础安装只带 CPU ORT 与 SenseVoice；GPU runtime 按 OS + EP 拆成独立可选包（Linux MIGraphX、Windows DirectML、Linux/Windows CUDA），各自单独目录、版本与 SHA。
  • voimed / voime-core 不依赖 worker crate；Rust workspace 的 feature unification 不能把 directml / migraphx / cuda 带进 daemon。必要时拆 workspace 或独立构建单元。
  • daemon 的 ORT_DYLIB_PATH / 动态库搜索路径只包含 CPU ORT；worker 在自己进程内设置 GPU ORT 路径，不继承 daemon 的 GPU 库路径。
  • Final 选择 CPU SenseVoice 时 worker 不启动；Final 选择 GPU 时只启动 worker，daemon 仍然只映射 CPU ORT，Preview 继续由 SenseVoice 处理。
  • 验收时必须在没有 ROCm / CUDA / DirectML 的机器上启动 CPU SenseVoice，并用 ldd / Process Explorer / /proc/<pid>/maps 确认 daemon 没有加载任何 GPU 库。

6.4 为什么否决文本后处理

问题结论
质量规则层覆盖有限；文本模型存在过度纠正、幻觉与语义改变风险。错别字更可能来自 ASR 模型或已删除的 CTC 路径，不应由文本后处理兜底。
延迟pipeline 单线程串行；增加一次文本推理会直接抬高收尾延迟，Continuous 还可能因队列满丢音频。
维护需要额外模型、分词器、词表、清单字段、守卫、回退、测试与许可证；收益不足以抵消长期成本。
定位产品链路只需要 ASR 文本；不做通用润色、改写、摘要或翻译，也不保存原文 / 候选对。
  • 不实现规则层、不引入文本纠错模型、不增加 --rewrite、清单字段或 IPC 消息。
  • 如果未来确实需要术语纠正，应另立提案，先证明它不会改变语义且满足延迟预算；不能作为本次 ASR 收敛的隐含后门。

6.5 长期维护边界

收敛后是“常驻 SenseVoice Preview + 可选 Final”：Final 走 CPU SenseVoice 或 GPU FireRed AED。两者共享 VAD、分段、pipeline、IPC、 active 与重启后端机制；需要单独维护的只有 ASR 模块、模型契约、金样测试与文档。

维护项频率估算
新增一个 ASR 后端一次性3–5 人日（贪心解码；不含模型训练）。
上游模型包更新每次模型升级0.5–1 人日 / 后端：SHA、张量、metadata、金样输出。
发布回归每个发布周期0.5–1 人日：CPU / GPU 金样、切换、回滚。
文档 / doctor每个发布周期0.25–0.5 人日（Preview / Final 路径共享大部分内容）。
默认 CI每次提交只跑模型无关的单元 / 清单测试；金样测试用环境变量启用，不把大模型放进默认 CI。
  • 主要纪律是每次模型更新同步 manifest、SHA、metadata 与金样，而不是维护两套 daemon 或两个版本。
  • 如果 GPU 路径长期没有质量收益，应删除 worker 与 runtime 包，而不是保留“永远实验”的第三条路径。

9. 风险

已接受的取舍：SenseVoice 常驻带来的 CPU / 内存开销可接受；Preview 与 Final 文本不一致可接受， Final 直接输入、不做呈现变化；Fcitx 动态枚举不可用时模型列表留空，不做补偿动作。

风险影响缓解
预卷把前一段尾音带入段首重复、串音或 CER 退化。从 200 ms 起测；按 PTT / Continuous 分别验证；端点延迟不退化；过长时回退。
ORT / ort 版本漂移或升级回归CPU int8 与 GPU FP16 的输出 / 延迟发生不可控变化；ort 升级可能编译失败或输出退化。每个发布锁定 ORT 版本与 build info；ort 实验每次只升一个版本；目标语料 + 黄金文本双门槛；保留 rc.12 回退；无收益不合并。
GPU 运行时泄漏进 daemonSenseVoice Preview / CPU Final 启动时被迫加载 ROCm / CUDA / DirectML，违背“CPU 不依赖 GPU”的目标。voimed / voime-core 只链接 CPU ORT；不依赖 worker crate；GPU 分进程、分 runtime 目录；CI 检查动态依赖与 /proc/<pid>/maps。
预卷收益不及预期段首缺字仍存在；不应扩大为 LFR / 量化改造。以目标语料结果决定是否保留；ORT 只按 §3.5 的条件实验处理，不把模型问题转成框架改造。
DirectML / MIGraphX / CUDA 版本矩阵安装失败、驱动不兼容、用户环境差异；AMD 上 CUDA / TensorRT 不可用。Linux MIGraphX 第一；Windows DirectML 与 NVIDIA CUDA / TensorRT 使用各自独立 runtime 包；doctor 预检；GPU Final 不可用时回退 CPU SenseVoice，Preview 继续。
FP16 显存不足 / 热降频加载失败或延迟抖动；1.1B FP16 约 2.2 GB 权重，加激活 / KV cache 后仍需 4–6 GB。声明 min_vram_mb；加载前检查；失败保留旧 Final 或回退 CPU SenseVoice；Preview 继续；不回退 FP32 / int8。
运行时包可执行文件安全runtime 包携带任意代码。只信任签名运行时；禁止第三方包自带可执行文件；安装需显式 opt-in。
firered 档缺少 SenseVoice 依赖GPU Final 能装但 Preview / CPU Final 不可用，启动失败。安装脚本强制安装并校验 requires；ListModels / doctor 报错；不允许只装 FireRed。
SenseVoice 许可证 / 署名权重按 FunASR Model License 分发；遗漏 LICENSE、模型名或 attribution 会造成合规问题。安装包保留 LICENSE / 模型卡；README Credits 标注来源；发布前核对模型卡条款。
模型包 SHA 变化官方重新上传导致校验失败。安装脚本重新计算并写入；运行期只信任本地清单。
active 或 SenseVoice 基础包缺失 / 错误启动失败、Final 加载错误，或 GPU 档缺少 Preview。启动时校验 Final + SenseVoice 基础包 / manifest.json / SHA / kind / requires；doctor 显示两者与解析目录；回滚只改 Final 指针；不提供 legacy 兼容。
重启 Final 加载失败新 Final 不可用，用户当前无法得到最终文本。先校验再停旧 Final；失败时回滚 active 并恢复旧 Final；Preview 不受影响；旧 Final 也失败才退出 daemon。
前端协议不匹配旧 Fcitx / 旧托盘无法连接。daemon 与两个前端同版本发布；旧前端收到 VersionMismatch 并提示升级；不静默降级。
UI 选择与 active 不一致用户以为已切换但仍在旧模型。打开界面时读取 active；选择后显示“待重启”；ListModels 同时返回 active / running。
Windows 设置进程无权限 / daemon 未启动点击重启失败。只写 active 并提示“下次启动生效”；由托盘启动 daemon；不直接杀进程。
长段稳定性20 / 30 s 段可能截断、重复或 CER 上升。Phase 0 纳入长段评测；SenseVoice 默认 20 s；GPU AED 30 s；不达标记为不可默认。
模型包体积 / 安装时间SenseVoice 基础包 + FireRed 权重 + runtime 包较大，首次安装慢。按档位安装；firered 才下载 FireRed；runtime 独立；记录体积；不提交权重。
旧版本升级 / 旧包混淆旧包被拒绝；用户可能误装 CTC / punc / AED CPU，或不知道要 clean install / 运行迁移脚本。旧包明确拒绝；安装脚本只提供新包；迁移脚本只覆盖上一版本 + 当前开发机；其他环境发布说明写清 clean install。
迁移脚本误操作旧模型或配置丢失，升级后无法回退。默认 --dry-run；执行前要求 daemon 停止；时间戳备份；失败自动恢复；不碰音频等与升级无关的用户数据。
