提案 — ASR v2：SenseVoice 收敛、GPU 后端与 VAD 选型

README USER CORE PROVIDER BUILD ｜ 状态：待评审 · 未实现 · 2026-11-01

本文给出 ASR 的单一决策：删除 CTC、保留 SenseVoice ITN、删除 SenseVoice + Punc 变体、 删除 AED CPU 推理、否决文本后处理、增加可选 GPU worker、保留 FireRedVAD 并评测替代品。 文档同时定义 SenseVoice 框架对齐、CPU / GPU 推理契约、模型包切换、配置界面与验收门禁。

本文按 clean break 设计：不承诺旧 schema、旧模型包、旧 active / legacy 布局、 旧前端协议兼容，也不提供迁移步骤或兼容层。升级按“重新安装新版本 + 新模型包”处理； 运行期失败回滚仍然保留，但它只回滚到本次运行已经加载的新 pipeline，不涉及旧版本迁移。

结论先行：SenseVoice 的少量错别字已经复现出框架侧原因，不是全部来自模型。 在当前 POC 与 sherpa-onnx 1.12.27 的对照中，7 条中文 / 中英混合样本有 2 条出现字符级差异， 另有 1 条标点差异；同一组 fbank 特征在 Python ORT 与 Rust ORT 下得到不同文本， 说明差异主要来自 ORT 版本 / 会话配置，LFR 边缘处理与分段缺少预卷是另外两个风险。 因此，本文把“先做推理框架对齐，再谈换模型”列为 Phase 0 的硬门槛。

2. 目标、非目标与设计边界

↑

2.1 目标

  • 把 CPU 默认后端收敛为唯一的 SenseVoice ITN；删除 CTC、SenseVoice-punc 与 AED CPU 路径。
  • 先完成推理框架对齐：固定 ORT 版本 / 会话、fbank 黄金回归、LFR 边缘处理与分段预卷，再评价模型。
  • 增加可选 GPU worker：只有 active 模型要求 GPU 时才启动，CPU 路径不加载任何 GPU 库。
  • 保留包级切换：models/active 指针 + 重启后端；切换不需要重新安装或替换二进制。
  • 复用现有 VAD、分段、音频采集、IPC、前端提交与 ONNX Runtime 边界。
  • 失败可回滚：新包加载或推理失败时恢复本次运行中已经加载的 pipeline；GPU 不可用时回退 CPU SenseVoice。
  • 保留 FireRedVAD 作为默认，并用目标语料评测 Silero v6 / TEN VAD 等替代品。

2.2 非目标

  • 不做运行时双模型热切换，也不在录音 / 识别过程中切换后端。
  • 不做 CPU AED；GPU 失败不自动加载 AED CPU。
  • 不实现文本后处理：不增加规则层、文本纠错模型、--rewrite、清单字段或 IPC 消息。
  • 不引入第二推理引擎、Python 运行时、云端 API 或 GPU 依赖到 CPU daemon。
  • 第一批不接 LLM；低于 FireRed AED 精度的 LLM 不测试。
  • 不承诺旧 schema、旧模型包、旧目录布局或旧前端协议兼容，也不提供迁移步骤。
  • 不做模型微调、领域自适应训练或通用文本润色。
  • 不把 SenseVoice 的语言 / 情感 / 事件标签暴露给前端；一期只消费文本。

2.3 设计边界

现有约束对新方案的要求
pipeline 只有一个工作线程，VAD / ASR / 标点串行 推理不能进入音频回调线程；新增阶段必须有明确预算，不能靠异步运行时规避串行成本。
音频通道与完成段队列有界，满时丢弃 GPU worker 超时、模型加载失败与后端重启都必须有背压与回退策略，不能拖垮 Continuous。

  • “默认单后端”不等于“单实现”：同一版本可以包含 CPU SenseVoice 与 GPU worker 两条路径，但同一时刻只加载一条。

3. 任务一：SenseVoice 错别字归因

↑

3.1 结论

部分是框架导致的，不能全部归因于 SenseVoice 模型。 在相同模型、相同音频、相同 use_itn=1 的条件下，当前 Rust POC 与 sherpa-onnx 1.12.27 的参考输出并不完全一致：

  • 7 条 16 kHz 中文 / 中英混合样本中，2 条出现字符级差异，且都是 POC 输出错字、参考输出正确。
  • 1 条出现标点差异（POC 少一个逗号）；多语种样例中粤语也出现标点差异。
  • 其余 4 条字符与标点一致。
  • POC 的 Hamming fbank 与 C++ 参考基本一致：最大绝对差约 3–5 × 10-4，均值约 10-6；2.wav 的差异不是 fbank 造成，但 3.wav 处于低置信边界，微小 fbank 差异也能翻转，不能完全排除。
  • 把同一组 POC fbank 特征送入 Python ORT 1.31.1，在 2.wav / 3.wav 上输出与 sherpa 参考一致；只有 Rust ORT 1.24.2 路径出现错字。这说明运行时版本 / 会话配置是已确认的框架侧原因之一。

因此，当前“少量错别字”至少有一部分是推理框架侧的可复现问题，而不是 SenseVoice 模型的上限。 但在修复框架之前，不能用它来判断 SenseVoice 是否值得替换，也不能把剩余错误全部归因于模型。

3.4 已定位的框架差异

3.4.1 ORT 版本 / 会话差异（已确认）

POC 使用 Rust ort 2.0.0-rc.12，随包 ONNX Runtime 为 1.24.2； sherpa-onnx 1.12.27 自带 ONNX Runtime 1.23.2； 对照脚本使用 Python onnxruntime 1.31.1。 三者加载同一份 int8 模型、同一套完整窗口 LFR / CMVN / 贪心解码；其中第二、三行使用同一组 POC fbank 特征，第一行使用参考自身 fbank。文本仍不一致：

路径ONNX Runtime2.wav3.wav
sherpa-onnx 1.12.27（参考） 1.23.2 就是平凡的啊… …把它时态写上去。
Python ORT + POC 的 Hamming fbank + 完整窗口 LFR 1.31.1 就是平凡的啊… …把它时态写上去。
Rust POC 1.24.2 就是平繁的啊… …把它时材写上去。
  • 同一组 POC fbank 特征在 Python ORT 1.31.1 下输出正确，说明运行时路径足以单独造成这两处差异；但 C++ fbank + Python ORT 在 3.wav 上又得到“时材”，说明该字符处于低置信边界，fbank 的微小差异也能翻转。
  • Rust POC 在 1 / 2 / 4 / 8 线程下输出稳定，说明不是线程数抖动；差异更可能来自 ORT 1.24.2 的 int8 kernel / 图优化行为。
  • 不要用“换个 ORT 版本”作为唯一修复：先固定版本、记录 build info，再用黄金文本测试验证；升级 ORT 也必须重跑黄金样本。
  • Hamming fbank 与 C++ 参考仍不是逐位一致：实测最大绝对差约 3–5 × 10-4，均值约 10-6；这属于可接受的浮点差异，但不能宣称逐位一致。Rust port 缺少 C++ 的 eps / use_log_floor 语义，属于低风险改进项，不是本次差异的唯一原因。

3.4.2 LFR 边缘处理不一致

FunASR 原始前端与 sherpa-onnx 新版本都对 LFR 做左 / 右边缘复制， 输出帧数为 1 + (T - 1) / shift；当前 POC 复刻的是 sherpa-onnx 1.12.27 的完整窗口行为： 只输出完整窗口，帧数为 (T - window) / shift + 1，短于一帧的音频直接返回空。 这会让段首 / 段尾的特征与训练前端不一致。

3.4.3 分段缺少预卷（高概率原因）

当前 Segmenter 从“第一个被 VAD 判为语音的帧”开始收集音频，没有保留语音起点之前的音频。 FireRedVAD 的流式参考配置包含 pad_start_frame=5（约 50 ms），而项目当前没有实现这个预卷； 中文的塞音 / 擦音起始、英文的爆破音很容易被切掉，表现为段首缺字或近音替换。 

当前：
VAD 判定 speech ──► 从这里开始收集
              ▲
              └── 之前的 50–300 ms 被丢弃

建议：
保留环形缓冲 ──► VAD 判定 speech ──► 从缓冲中回取 200–300 ms
  • 预卷不改变 VAD 的判定，只改变交给 ASR 的音频范围；它是最低风险、最可能直接减少“段首错字”的改动。
  • PTT / Toggle 模式可以在按键按下时就开始缓冲，预卷成本更低；Continuous 模式需要常驻环形缓冲。
  • 预卷长度不是越长越好：过长会把前一段的尾音带进来，建议从 200 ms 起测，按目标语料调整。

3.6 建议的归因顺序

1. ORT 版本 / 会话对齐
   ├── 固定 ONNX Runtime 版本，记录 build info
   ├── 固定图优化级别、线程数、EP
   └── 同一组特征 + 同一模型 + 同一 LFR 的黄金文本

2. fbank 黄金回归
   ├── Hamming fbank 与 C++ 参考逐元素比较
   ├── 当前差距约 3–5 × 10⁻⁴，先冻结基线
   └── 若要求逐位一致，改用 C++ 绑定

3. LFR 对齐
   ├── 完整窗口模式与边缘复制模式同时保留
   ├── 目标语料 A/B
   └── 与 FunASR / sherpa 参考输出对比

4. 分段预卷
   ├── Continuous：常驻 200–300 ms 环形缓冲
   ├── PTT / Toggle：按键即开始缓冲
   └── 段首 / 段尾黄金测试

5. 模型与参数
   ├── int8 vs fp32
   ├── language auto vs zh

  • 每一层都要有“参考输出 + POC 输出 + 差异原因”的记录；不要只报最终 CER。

4. 目标架构：CPU daemon + 可选 GPU worker

↑

CPU 推理（VAD、SenseVoice、FireRedPunc）本来就一直需要，继续留在 voimed / voime-core 内，使用 CPU-only ORT。 GPU 只作为可选能力：只有 active 模型要求 GPU 时，才拉起独立的 voime-asr-worker 进程。 这样 CPU 路径不增加额外进程，GPU 也不污染 CPU 路径。

  • voimed / voime-core 使用 CPU-only ORT；不加载 GPU 库。
  • voime-asr-worker 是唯一加载 DirectML / MIGraphX / CUDA 的进程，只在 GPU 模型时启动。
  • VAD 与 FireRedPunc 始终在 daemon 的 CPU ORT 上；GPU 模式下也不搬进 worker。
  • 选择 CPU 模型时 worker 不启动；切换回 CPU 时停掉 worker 并释放显存。
组件职责不负责
voimed 音频采集 / 重采样、环形缓冲、分段、前端 IPC、目标注入、模型选择、GPU worker 生命周期。 GPU 库、GPU 会话、具体 GPU 模型解码。
voime-core CPU-only ORT；FireRedVAD、SenseVoice、FireRedPunc；fbank / LFR / CMVN；Final 文本。 GPU 模型、GPU EP、前端 IPC、目标注入。
voime-asr-worker GPU-only ORT；FireRed AED FP16；返回原始文本与耗时。 VAD、分段、标点、CPU ASR、前端 IPC。
模型包 权重、清单、SHA、VAD / Punc、可选 GPU 模型。 不包含运行时库、不写日志、不联网。
GPU runtime 包 voime-asr-worker + GPU ORT + EP 库；可选安装。 不进入模型目录，不被 active 直接选择。

4.3 SenseVoice CPU 推理契约

SenseVoice 是唯一 CPU 默认后端。包固定为 sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2024-07-17， use_itn=1，punc=builtin；不再维护 noITN + FireRedPunc 变体。

项目契约
模型234M 参数，int8 ONNX 约 229 MiB；输出 25055 类；固定 2024-07-17 权重。
fbank80 bin、25 / 10 ms、hamming 窗、snip_edges=true、normalize_samples=0（输入乘 32768）。
LFR窗口 7、帧移 6；Phase 0 同时保留完整窗口与边缘复制，目标语料 A/B 后冻结；默认优先 FunASR 训练口径（首尾边缘复制），但以 A/B 结果为准。
CMVN560 维；(x + neg_mean) * inv_stddev；长度必须等于 80 × 7。
输入x[1,T,560] f32、x_length[1] i32、language[1] i32、text_norm[1] i32。
输出logits[1,T',25055] f32。
解码贪心 CTC：argmax → 合并重复 → 去 blank 0；有效长度 min(T', T + 4)，跳过前 4 个语言 / 情感 / 事件 / 文本规整 token。
语言auto=0、zh=3、en=4、yue=7、ja=11、ko=12；默认 auto，不硬编码 zh。
ITN固定 use_itn=true；with_itn=14、without_itn=15；Partial 与 Final 使用同一模式。
标点模型内置；不加载 FireRedPunc。
Partial支持；沿用同一后端与同一 text_norm，不额外加标点。
最大段长建议 20 s；用 20 / 30 s 样本验证后再冻结。

SenseVoice::transcribe(features)
├── 判断 features.is_empty() → AsrOutput::default()
├── ApplyLfr(features, 7, 6) → lfr_frames
├── 判断 lfr_frames 的维度 == 560
├── 逐帧 (x + neg_mean) * inv_stddev → cmvn_frames
├── 构造 x[1, T, 560] f32
├── 构造 x_length[1] i32 = T
├── 构造 language[1] i32
├── 构造 text_norm[1] i32 = with_itn
├── Session::run({x, x_length, language, text_norm})
├── 取 logits[1, T', 25055]
├── valid = min(T', T + 4)
├── greedy_decode(logits, valid, 25055) → ids
├── 判断 ids.len() >= 4 → 跳过前 4 个特殊 token
└── CtcTokenizer::decode(ids[4..])

  • 不要从 tokens.txt 推断语言 / ITN id；模型升级后容易错位。
  • tokens.txt 的 SHA-256 为 f449eb28dc567533d7fa59be34e2abca8784f771850c78a47fb731a31429a1dc；安装脚本以实际文件重新计算并写入清单。

  • 如果 ids 少于 4 个，说明模型没有输出完整前缀；返回错误或空文本，不要把剩余 token 当正文。

5. 任务二：可选 GPU worker 后端

↑

5.1 目标与非目标

目标非目标
CPU 推理留在 daemon；GPU 推理放进可选 worker；CPU 模型不启动 worker。 不做 CPU runtime 独立进程；CPU 本来就是常驻路径，再拆一个进程只增加 IPC 与生命周期成本。
GPU worker 与 daemon 库隔离；GPU 崩溃不能带崩 CPU 路径。 不在 daemon 内直接加载 GPU EP；不做线程级“伪隔离”。
GPU worker 是独立二进制包；可单独安装 / 升级 / 卸载。 不引入第二推理引擎；worker 仍使用 ONNX Runtime。
CPU 路径无 GPU 依赖；GPU 不可用时 CPU SenseVoice 继续工作。 不做 CPU AED；GPU 失败不自动加载 AED CPU。

5.2 方案比较

方案收益代价 / 风险结论
A. 在 daemon 内直接使用 ORT GPU EP 实现最短；复用 SessionFactory。 GPU 库进入 daemon；CPU 路径无法保证不加载；GPU 崩溃带崩 daemon。 不采用。
B. 可选 GPU worker 进程 CPU daemon 只带 CPU ORT；GPU 库只在 worker；崩溃隔离；可按需启动 / 停止。 需要协议、生命周期、超时与安全校验；多一个进程（仅 GPU 模式）。 采用。
C. CPU / GPU 两个 runtime 进程 CPU 推理也完全独立。 VAD / Punc 本来就要常驻；再拆一个 CPU 进程增加 IPC、生命周期与重复模型，收益不足。 不采用。
D. 动态库插件 调用开销低。 插件与 daemon 同进程；GPU 崩溃 / 库版本仍带崩 daemon。 不采用。
E. 外部推理服务器 吞吐高；LLM 生态成熟。 Python / CUDA 依赖重；启动慢；桌面安装复杂。 只做离线评测。

5.3 GPU worker 生命周期

  • daemon 启动时只创建 CPU pipeline；GPU worker 仅在 active 模型 backend.kind = worker 时启动。
  • 选择 CPU 模型时 worker 不启动；切换到 CPU 模型时先停 worker，释放显存。
  • worker 退出即释放 GPU 内存；daemon 不持有 GPU 会话，也不初始化 GPU。

5.6.1 CPU / GPU 运行时隔离

硬规则：CPU daemon（voimed / voime-core）只加载 CPU ORT；voime-asr-worker 是唯一允许加载 GPU ORT / EP 库的进程。 只要把 GPU EP 编进 daemon，就无法保证 CPU 推理不碰 ROCm / CUDA / DirectML。

路径进程ORT 构建模型加载 GPU 库
SenseVoice CPU voimed / voime-core ORT CPU only SenseVoice int8 + VAD + Punc 否
FireRed AED GPU voime-asr-worker DirectML / MIGraphX FireRed AED FP16 是，仅 worker
VAD / Punc（GPU 模式下） voimed / voime-core ORT CPU only FireRedVAD + FireRedPunc 否
  • 基础安装只带 CPU ORT 与 SenseVoice；GPU runtime 是独立可选包，单独目录、单独版本、单独 SHA。
  • voimed / voime-core 不依赖 worker crate；Rust workspace 的 feature unification 不能把 directml / migraphx / cuda 带进 daemon。必要时拆 workspace 或独立构建单元。
  • daemon 的 ORT_DYLIB_PATH / 动态库搜索路径只包含 CPU ORT；worker 在自己进程内设置 GPU ORT 路径，不继承 daemon 的 GPU 库路径。
  • 选择 CPU 模型时 worker 不启动；选择 GPU 模型时只启动 worker，daemon 仍然只映射 CPU ORT。
  • 验收时必须在没有 ROCm / CUDA / DirectML 的机器上启动 CPU SenseVoice，并用 ldd / Process Explorer / /proc/<pid>/maps 确认 daemon 没有加载任何 GPU 库。

FireRedAed::transcribe(features)
├── 判断 features.is_empty() → AsrOutput::default()
├── 逐帧 (x - cmvn_mean) * cmvn_inv_stddev → 80 维 fbank
├── 构造 x[1, T, 80] f32 / x_lens[1] i64
├── encoder.run({x, x_lens}) → cross_k / cross_v
├── 按 metadata 分配 self KV cache
├── decoder.run(tokens=[sos], self_k, self_v, cross_k, cross_v, offset=0)
├── 循环：argmax(logits) → 追加 token / 更新 self KV cache / offset
├── 停止条件：eos / max_len / max_token_per_second
└── CtcTokenizer::decode(ids)
  • AED 的 fbank / CMVN 与 FireRed 家族一致；不做 LFR。
  • sherpa-onnx 当前对 FireRed AED 只实现 greedy_search；beam search 不进入一期验收。
  • AED 默认 partial=false；如果后续证明预览可接受，再通过 AsrOptions.partial 打开。
  • worker 接收原始 PCM，不接收 daemon 算好的 fbank；GPU 模型可以有自己的前端。

6.4 为什么否决文本后处理

问题结论
质量规则层覆盖有限；文本模型存在过度纠正、幻觉与语义改变风险。错别字不一定是文本层问题，先修框架更可靠。
延迟pipeline 单线程串行；增加一次文本推理会直接抬高收尾延迟，Continuous 还可能因队列满丢音频。
维护需要额外模型、分词器、词表、清单字段、守卫、回退、测试与许可证；收益不足以抵消长期成本。

7. 任务四：VAD 选型

7.1 现状

当前使用 FireRedVAD 的流式 ONNX 模型（stream-vad.onnx，约 2.2 MB），10 ms 帧移， 默认阈值 0.5；VAD 与 ASR 共用同一套 Rust fbank。现有实现没有预卷、没有概率平滑、 阈值与静音时长硬编码在 Segmenter / VadConfig 中。

7.5 结论

保留 FireRedVAD，不替换。 它在公开多语种 VAD 基准上领先 Silero / TEN / FunASR / WebRTC，且已经是 Apache-2.0、已有流式 ONNX， 与项目当前“CPU 低延迟、离线、单模型包”的边界一致。当前的问题主要是预卷、平滑、阈值与 fbank 回归， 不是 VAD 模型本身。

  • Silero VAD v6 作为首选回退：生态成熟、MIT、目标机器上若 FireRedVAD 出现兼容性问题可直接替换。
  • TEN VAD 作为低延迟 / 低内存备选：需要先确认附加许可条款，再做目标语料 A/B。
  • 不采用 FunASR FSMN / WebRTC 作为默认：前者误报高，后者漏检高。
  • 如果目标语料证明 FireRedVAD 的端点延迟不达标，再按 §7.3 的门槛替换，而不是凭公开榜单切换。

  • 单独包含 50–100 条 20 / 30 秒长段，覆盖连续说话、句中停顿、数字列举与中英混合；用于验证截断、重复、丢段与长段 CER。
  • 分层以中英文为主：纯普通话、中文专名 / 术语、数字 / 日期 / 金额、中英混合、英文；方言 / 口音、噪声 / 远场作为次级覆盖。
  • 每条语音有人工参考文本；参考文本统一标点、大小写与数字写法，另存一份“原始口语”版本用于分析 ITN。
  • 包含“当前系统已经正确”的负样本，用来观察新模型是否引入新错误。
  • 测试集不参与模型选择；如果要用它调 use_itn / 标点策略，另留开发集。
  • 评测集必须与 VAD / 分段策略一起冻结；只换模型、不换前端，否则差异无法归因。
  • 长段样本单独统计，不要用短句平均值掩盖截断 / 重复问题。

ORT / 前端对齐工作量超预期Phase 0 拖延，后续模型比较无法可信。固定 ORT 版本与 build info；fbank 黄金回归；LFR / 预卷测试；必要时用 sherpa 参考生成器。

LLM 重复 / 幻觉识别文本被改写或无限生成。第一批不接 LLM；只有 FireRedASR2-LLM 条件项才验收重复 / 不终止；设置 max tokens / 超时。

Windows 设置进程无权限 / daemon 未启动点击重启失败。只写 active 并提示“下次启动生效”；由托盘启动 daemon；不直接杀进程。

模型包体积 / 安装时间GPU 权重与 runtime 包较大，首次安装慢。CPU / GPU / runtime 分包；安装脚本按需下载；记录体积；不提交权重。
旧安装 / 旧包混淆用户按旧说明安装 CTC / punc / AED CPU。旧包直接拒绝；安装脚本只提供新包；产品文档只保留本文的决策；不写迁移步骤。
clean break 升级旧安装不能原地升级，必须重新安装 + 新模型包。发布说明明确“不兼容旧版本 / 旧包”；不提供迁移向导；安装脚本只支持新装。

待决策问题：

  • AMD 硬件下先做哪个平台？建议优先用户实际使用的平台：Windows 用 DirectML，Linux 用 MIGraphX；不把 CUDA 作为前提。
  • AMD 运行时如何打包？Windows DirectML 依赖系统组件，安装包较小；Linux MIGraphX / ROCm 依赖较重，建议运行时包自带并做版本校验。
  • GPU runtime 包是否允许模型包自带可执行文件？建议第一阶段不允许，只允许项目签名的 voime-asr-worker runtime。
  • VAD 替代品是否进入产品包，还是只做离线评测？建议先只做评测，FireRedVAD 继续默认。
  • 本文明确不保留过渡版本、不做兼容 / 迁移；如果未来要改变这一点，需另立提案。
