1. 决策摘要

↑

1.1 决策表

问题决策
是否为 Windows 新建一个项目并复制代码？ 不。至少现在不。继续同一个仓库；共享引擎与协议，平台前端作为独立构建根。
哪些部分放在同一个 Cargo workspace？ voime-core、voime-ipc、voime-transport、voimed、voime。这五个 crate 同时服务 Linux 与 Windows。
Windows 前端放哪里？ frontends/windows/，独立 Cargo workspace；TSF DLL 作为其下的 C++/CMake 子工程。
Fcitx addon 放哪里？ 目标形态为 frontends/fcitx/；文档已先行迁移，源码迁移可晚做，不阻塞 Windows。
named pipe / Unix socket 怎么处理？ 协议与 framing 共享；传输实现放入 voime-transport 的平台模块，daemon 与 CLI 只依赖 Endpoint / Stream 契约。
用什么选择平台实现？ 用 Cargo 的 cfg(unix) / cfg(windows) 与 target-specific dependencies；不引入用户可见的 --features unix / --features windows 开关。
真正的 Windows 输入法（TSF）放第几阶段？ MVP 之后的可选阶段（P4）。先完成后台听写 MVP；TSF 作为可选 C++ 前端，不污染核心 crate。
迁移方式 增量重构；每一步保持 Linux 可构建、可测试；不做一次性的目录大搬家。

1.2 为什么不是新项目

  • 最贵的部分不是 socket，而是识别链路。复制 voime-core 会立刻产生两份 ASR / VAD / pipeline 维护成本。
  • named pipe 换项目也要写。新项目不会让平台适配消失，只会把协议、模型、测试与发布再拆一份。
  • 当前仓库已经混合 Cargo 与 CMake。再加一个 Windows 前端不是新的工程形态；真正的新增是“平台前端构建根”，不是“第二个产品核心”。
  • 拆分时机应跟产品走。如果 Windows 前端将来成为独立产品、独立团队或独立发布节奏，再搬 frontends/windows，而不是搬 voime-core。

1.3 适用范围

项目说明
LinuxRust daemon / CLI / TUI + Fcitx5 addon；现有行为与验收标准不变。
WindowsRust daemon / CLI / TUI + 新的 Windows 前端；MVP 为后台听写，TSF 可选。
共享协议换行 JSON、消息类型、角色、Mode / segment / Partial / Final 语义。
不在本文范围Windows 输入法的具体 UI 视觉、模型再导出、安装器视觉、TSF 的具体实现细节。

2. 目标与非目标

↑

2.1 目标

  • 单一事实来源：ASR、VAD、标点、pipeline、模型 manifest 与协议只维护一份。
  • 平台前端可替换：新增平台不需要修改 voime-core 的业务逻辑。
  • 平台差异收敛：OS API 只出现在 voime-transport 与 frontends/；daemon 与协议保持平台无关。
  • 构建互不拖累：Linux 构建不编译 Windows 专用 crate；Windows 构建不要求 Fcitx5 / CMake Linux 依赖。
  • 可验证：共享 crate 在两个平台跑同一组协议/状态测试；平台适配器有各自的 conformance tests。

2.2 非目标

  • 不做跨平台 UI 抽象或统一的热键/预览/提交接口；这些是前端行为，不是核心机制。
  • 不追求“一套 transport 实现跑所有平台”；Unix socket 与 named pipe 各自原生实现。
  • 不把 Fcitx5 的 InputContext 抽象成 Windows 也能用的通用输入上下文。
  • 不在第一阶段做 TSF；不在第一阶段把 frontends/windows 合入根 workspace。
  • 不为 Windows 复制一套 ASR / pipeline / 模型包。

3.3 依赖方向

  • 前端只依赖协议与 transport，不依赖 voime-core；ASR / 模型只在 daemon 内。
  • voime-transport 是共享 crate，但 Unix / Windows 实现互不复用；共享的是契约。
  • Fcitx 与 TSF 是 C++/CMake 构建根，不进入 Cargo workspace。

3.4 依赖规则

规则说明
voime-core 不依赖其它 voime-* crate保持引擎独立；不得引入 IPC、CLI、Fcitx、Windows API。
voime-ipc 不依赖 transport协议只描述消息与字节 framing；不关心 socket / pipe。
voime-transport 不依赖 core / ipc它只处理字节流与端点；需要消息类型时由调用方组合。
voimed 依赖 core + ipc + transportdaemon 是唯一把识别、协议、传输组合起来的共享二进制。
voime 依赖 ipc + transportCLI / TUI 不加载模型；只做客户端与控制。
前端依赖 ipc + transport（若为 Rust）Windows 托盘可直接复用消息类型与命名管道客户端；C++ TSF 只依赖协议契约与测试样例。
前端不依赖 core避免把 740 MiB 模型或 ONNX Runtime 拖进前端；TSF DLL 更不应加载模型。

5. 边界契约

↑

5.1 transport 契约

Endpoint / Listener / Stream 与 bind / connect 的完整契约见 voime-transport USER §4； Unix / named pipe 的平台差异与安全细节见 voime-transport PROVIDER。本文不再复制接口定义。

  • P0 完成标准：daemon / CLI 不再直接 import std::os::unix；transport 之后只暴露字节流与端点。
  • Endpoint 不进入 voime-core::Config；core 只拥有模型、音频与线程配置。

5.2 平台传输实现

关注点Unix adapterWindows adapter
端点文件系统路径\\.\pipe\voime-<session>-<user> 命名管道
权限父目录 0700、socket 0600当前用户 DACL；PIPE_REJECT_REMOTE_CLIENTS
陈旧端点启动时尝试连接；失败则删除旧 socket管道句柄关闭即消失；检查已有 daemon
accept非阻塞 + 短睡眠，或可中断 accept阻塞 ConnectNamedPipe 或 overlapped；shutdown 可取消
读写分离try_clone 复制 fdDuplicateHandle
关闭shutdown + dropDisconnectNamedPipe / CloseHandle
错误映射io::Error + 路径上下文io::Error + Win32 错误码/管道名上下文
  • Windows 后端优先原生 named pipe；uds_windows 只作为 MVP 备选，不进入核心契约。
  • 不使用 loopback TCP 作为默认传输：防火墙提示、端口冲突、同机任意进程可连接。

5.3 前端行为契约

职责要求
握手连接后发送 Hello { role: Frontend, version, config }；版本不匹配时清理并重连。
配置所有权前端拥有 Mode / Hotkey，并通过 Hello / Configure 同步给 daemon。
开始/结束PTT / Toggle 在按键事件中绑定目标后发送 Start / Stop；continuous 由 daemon 的 SegmentStarted 驱动。
目标一个语音段只绑定一个目标；段内不改变；提交前复核目标仍有效。
Partial收到 Partial 显示临时文本；为空时不清空上一行；不是最终提交。
Final只提交 segment_id 匹配当前目标的 Final；先清空临时窗口，再提交。
失焦目标失焦/销毁时不提交；Toggle 会话停止；最终文本保留在 daemon 历史。
断线daemon 不可用时放行热键、清空临时窗口、定时重连；不阻塞普通键盘输入。
安全只连接当前用户可访问的端点；不记录按键、音频或识别文本到磁盘。
  • 这份契约适用于 Fcitx addon、Windows 听写前端和未来 TSF；实现可以不同，行为必须一致。Linux 实现见 fcitx-addon USER，Windows 实现见 windows USER。
  • 不为跨语言前端强行设计 Rust trait；消息语义 + 金样测试是共同契约。

5.4 C++ 前端与协议复用

前端传输协议复用方式
Fcitx addon（C++）Unix socketnlohmann/json + 现有 ipc.cpp；共享 tests/fixtures/ipc
Windows 托盘（Rust）named pipe直接依赖 voime-ipc + voime-transport
TSF DLL（C++，可选）named pipe小型 C++ pipe client + nlohmann/json；共享金样与协议版本
  • TSF 是可选阶段，不为它提前造跨语言 transport 绑定；先让 Rust tray 走通，再决定 C++ 客户端的复用程度。
  • 任何 C++ 客户端都必须通过同一组 Hello / Role / framing / 非法消息测试。

6.2 cfg 与 feature 规则

crate允许的 cfg禁止
voime-core无 OS cfg；仅测试/调试 cfgcfg(windows)、Fcitx、socket、路径

  • 不用 --features unix / --features windows 选择平台；Cargo target 已经能表达，feature 会造成依赖统一与误编译。
  • 测试用的内存 transport 可以放在 voime-transport 的 cfg(test) 或 dev-dependency，不作为生产 feature。

6.3 workspace 边界

# 根 Cargo.toml
[workspace]
members = [
    "crates/voime-core",
    "crates/voime-ipc",
    "crates/voime-transport",
    "crates/voimed",
    "crates/voime",
]
exclude = ["frontends/windows"]

# frontends/windows/Cargo.toml
[workspace]
[package]
name = "voime-windows"

[[bin]]
name = "voime-tray"
path = "src/main.rs"

[dependencies]
voime-ipc = { path = "../../crates/voime-ipc" }
voime-transport = { path = "../../crates/voime-transport" }
  • frontends/windows 使用独立 workspace 与独立 Cargo.lock，避免 Windows-only 依赖污染 Linux 的 cargo test --workspace。
  • 共享 crate 通过 path dependency 复用，不是复制；CI 同时检查根 workspace 与 Windows workspace。
  • 共享 crate 与两个前端跟随同一仓库 tag 发布；协议版本独立管理。未来拆仓库时再把共享 crate 提升为 semver 依赖。
  • 如果未来需要单 lockfile，可把 Windows crate 合入根 workspace，但必须解决 Linux 上 cargo test --workspace 的编译目标问题；当前提案不采用。

6.4 构建命令

# Linux：共享 crate + daemon/CLI
cargo build --release -p voimed -p voime
cargo test -p voime-core -p voime-ipc -p voime-transport -p voimed -p voime

# Linux：Fcitx addon
cmake -S frontends/fcitx -B build/fcitx -DCMAKE_INSTALL_PREFIX=/usr
cmake --build build/fcitx

# Windows：共享 crate + daemon/CLI
cargo build --release -p voimed -p voime
cargo test -p voime-core -p voime-ipc -p voime-transport

# Windows：托盘前端
cd frontends/windows
cargo build --release

# Windows：可选 TSF DLL
cmake -S frontends/windows/tsf -B build/tsf-x64 -A x64
cmake -S frontends/windows/tsf -B build/tsf-x86 -A Win32
cmake --build build/tsf-x64 --config Release
cmake --build build/tsf-x86 --config Release
  • Fcitx 文档与源码均位于 frontends/fcitx；迁移完成标准见 P4。
  • Windows 的 CMake 命令需要 Visual Studio / Windows SDK 环境；-A Win32 与 -A x64 分别产出 TSF 的 32/64 位 DLL。

  • 共享 crate 必须在两个平台都跑测试；平台 transport 的 conformance tests 在各自 runner 上跑。
  • Linux 不构建 frontends/windows；Windows 不要求 Fcitx5 或 Linux 音频头文件。
  • cargo check --target x86_64-pc-windows-msvc 可作为 Linux 上的快速反馈，但不能替代 Windows 上的链接/COM/TSF 验证。

7. 迁移步骤

↑

阶段动作完成标准
P0 新增 voime-transport；把 Unix socket 从 voimed / voime 中移出；Endpoint 从 voime-core::Config 移出；平台默认目录（模型/日志/配置）移出 core。 Linux 行为不变；daemon/client 不再直接 import std::os::unix；transport 测试通过。
P1 协议去 Fcitx 化：Role::Frontend / FrontendConfig / FrontendState；保留旧值别名；协议版本按兼容窗口处理（过渡期接受 v1，或先升级 addon）。 旧 Fcitx addon 仍可连接；TUI/日志不再出现 Fcitx 专用词。
P2 Windows named pipe 后端 + Windows CI；daemon/CLI 在 Windows 启动、握手、采集。 Windows 上 voimed + voime 可用；管道 ACL 测试通过。
P3 新增 frontends/windows MVP：托盘、热键、目标绑定、浮层、SendInput。 验收应用集合内闭环；目标失焦不误提交；安装/登录启动可用。
P4 源码迁移：把 fcitx-addon 移到 frontends/fcitx；TSF C++ 子工程作为可选后续。 目录与文档一致；Linux/Windows 各自构建不受影响；TSF 未启用时不构建。
  • 每个阶段单独合并，不做“一次搬完”的大重构。
  • P0/P1 是共享代码的改造，不依赖 Windows 前端；先做可以让 Linux 继续可用。

8. 验收与评审规则

↑

规则检查
核心无平台 APIvoime-core / voime-ipc / voimed 不出现 std::os::unix、Win32、Fcitx 头文件、socket/pipe 类型。
前端无模型Windows 托盘 / TSF DLL 不链接 ONNX Runtime，不加载模型。
共享测试双平台core / ipc / transport 的测试在 Linux 与 Windows CI 都通过。
transport 契约测试bind/connect/收发/EOF/大消息/多客户端/关闭唤醒在 Unix 与 named pipe 都通过。
Linux 不回归Fcitx addon、Unix socket、systemd、模式/热键行为与现有验收一致。
Windows 闭环目标应用内完成热键 → Partial → Final → 上屏；失焦不误提交；无网络。
适配器薄平台前端不出现 ASR / 分段 / 会话状态逻辑；transport adapter 不出现业务分支。
协议版本消息形状改变必须提升 PROTOCOL_VERSION；旧客户端有明确错误或兼容路径。

9. 开放问题

↑

问题建议
Windows 前端用 Rust 还是 C++？MVP 托盘用 Rust；TSF DLL 用 C++/COM。不要为了统一语言把 TSF 写成 Rust 服务。
TSF 注册成 keyboard TIP 还是 speech TIP？先做 keyboard TIP 单应用原型验证提交；speech TIP 是否能与键盘输入法并行另行 spike。
模型安装目录Windows 先每用户 %LOCALAPPDATA%；如果要共享给多用户，再评估 %PROGRAMDATA% 与权限。
多会话 / RDP先每会话 daemon；每个会话一份模型内存。若不可接受，再设计共享 daemon + 会话路由。
未来是否拆仓库当 Windows 前端成为独立产品/团队/发布节奏时，只拆 frontends/windows；核心通过 path 或版本化 crate 共享。
